### 1.3 术语和范围边界

- “完整双向载荷/应用层内容”在本方案中机械定义为：健康捕获窗口内，每个 TCP 连接实例按方向去重、处理乱序和重传后得到的全部 TCP payload 字节，以及每个 UDP 会话按方向、时间和报文边界保留的全部 UDP payload 字节。
- 每个方向必须提供字节数、SHA-256 和无损 Base64；HTML 可从同一份 Base64 按需显示完整十六进制，并在全部字节构成有效 UTF-8 时显示完整文本。十六进制、文本和 Base64 不得来自三份独立计算结果。
- TLS、应用自定义加密、压缩或编码的数据，在没有密钥或既有解码器时，完整内容指精确密文/编码后 payload 字节；不得声称已解密。既有 listener 已产出的协议字段或明文 NBI 继续展示，但不是捕获完整性的事实源。
- TCP 首次观测可能位于既有连接中段；“完整”以本次健康捕获窗口为边界。首个已观测序号之前的未知历史不构造数据。已观测区间内部的未填补序号缺口或冲突重叠属于完整性失败。
- `DumpPackets=Yes` 是本方案完整载荷报告的前置条件。显式配置 `DumpPackets=No` 时保持现有 NBI 报告能力，但报告必须明确标注“未启用捕获，不能提供捕获支持的完整载荷”，不得显示完整或健康裁决；这不是捕获失败后的降级路径。
- 完整载荷范围为 TCP/UDP。ICMP 和其他非 TCP/UDP 协议继续保留在 PCAP 中，不在本方案中虚构“应用层重组”。

### 2.2 根因链

#### `ROOT-001`：GUI 启动的同步控制台日志阻塞 WinDivert 单线程热路径

1. `fakenet/gui/launcher.py` 的 `build_dev_command` 与 `build_frozen_command` 只添加日志文件、stop flag 和 `-p`，未添加已经存在的 `-n/--no-console-output`。
2. `fakenet/fakenet.py::_configure_startup_logging` 先安装 UTF-8 文件 handler；未指定 `-n` 时又安装同步 `StreamHandler`。
3. `fakenet/diverters/windows.py::_handle_policy_packet` 在写 PCAP 后、真正 `_send_packet` 前同步记录 `ALLOW_TAKEOVER_SINK`。同一个 WinDivert 接收线程承担写包、策略、日志和发送。
4. 实测在 11:25:17.625 已把 236 字节出站 payload 写入 PCAP，直到 11:29:44.172 才继续处理；热路径统计为 `pcap_max_ms=0`、`send_max_ms=16`、`cycle_max_ms=266547`。同时 MainThread 于 11:29:36 仍能写文件日志，排除了文件 handler 全局阻塞。
5. 因此，应用内已证根因是 GUI 会话错误启用了同步控制台输出，使外部控制台停滞能够阻塞 WinDivert 热路径。造成外部控制台停滞的具体 Windows UI 行为尚未证实；本方案不把 QuickEdit 或其他猜测写成根因。

#### `ROOT-002`：现有“健康”只验证双 writer 一致，不验证捕获覆盖

1. `DualPcapWriter` 的 `healthy=True` 只证明 raw/converted 写入数量一致、输入未拒绝和关闭成功。
2. `windows.py` 只把长循环间隔写成 `WINDIVERT_RECV_CYCLE_GAP`，没有把已超过队列时间的捕获空窗转为 `PcapWriteError`。
3. 主 handle 的队列参数查询是 best-effort；实测没有 `WINDIVERT_QUEUE_PARAM` 成功标记，却把代码后备值 2000 写入 gap 日志。随仓库 `pydivert-2.1.0` 的常量说明与该后备值并不一致，当前阈值不是可审计事实。
4. 入站 record-only handle 也没有固定/回读队列参数和 recv-cycle 完整性判断。
5. WinDivert 官方合同说明队列时间、长度或字节容量不足时包可能被丢弃，应用必须及时调用 `Recv`；因此 writer 成对健康不能替代捕获覆盖健康。

#### `ROOT-003`：HTML 的事实源是 listener NBI，不是 PCAP 中的完整流

1. `fakenet/diverters/diverterbase.py::logNbi` 只有在 `sessions[orig_sport]` 存在时才收集 listener NBI；精确 Ubuntu sink 的 `ALLOW_TAKEOVER_SINK` 路径不进入 Windows 本地 listener，因此不会产生 NBI。
2. `generate_html_report` 仅以 `self.nbis` 渲染模板，并且当前在捕获关闭之前执行，不能基于已经封口的 PCAP 给出稳定报告。
3. `fakenet/listeners/RawListener.py::collect_nbi` 明确只保留 `hexdump_lines[:16]`；模板也明确显示 `showing first 256 bytes`。
4. `PROCESS_FLOW` 日志含进程、五元组和 disposition，但 `_flow_audit` 只保留时间戳并会 TTL/容量清理；生产报告若再解析文本日志会形成第二事实源且不能保证全会话数据。

- 不在仓库提交样本、原始 payload、PCAP 或包含 payload 的 HTML；它们只保留在忽略的本地 `dist/` 证据目录。

## 3. 固定设计决定

| 决定 ID | 固定决定 | 依据 |
|---|---|---|
| `DEC-001` | GUI 的 dev/frozen 启动命令必须添加现有 `--no-console-output`；手工 CLI 未传该选项时的控制台输出行为不变。GUI 实时日志继续读取文件日志。 | `ROOT-001`；最小直达修复，不扩张为全局异步日志重构。 |
| `DEC-002` | 主 WinDivert handle 与入站 record-only handle 都必须显式设置 queue length=`8192`、time=`2048 ms`、size=`33554432 bytes` 并逐项回读相等。任一 set/readback 失败即为捕获启动失败，不使用未证实默认值。 | `ROOT-002`、`SRC-TECH-001`；绑定 wheel 的上界和实测缺失参数标记。 |
| `DEC-003` | 任一捕获线程从一次 `recv()` 返回到下一次进入 `recv()` 的间隔大于或等于该 handle 已回读的 queue time 时，记录一次结构化完整性失败并调用既有 `_record_capture_failure(PcapWriteError)`；不得继续生成成功报告。 | `SRC-USER-002`；达到最小排队时间后已经无法排除队列丢包。 |
| `DEC-004` | `PCAP_DUAL_SUMMARY` 必须分别表达 writer 健康和 coverage 健康；只有队列参数已绑定、主/入站捕获无 fatal gap、writer 成对健康且重组无缺口/冲突时，完整捕获总裁决才可为健康。 | 避免 `healthy=True` 多义。 |
| `DEC-005` | 报告的数据事实源是捕获关闭后的 raw PCAP；流归属来自运行时首次计算后写入的会话级内存记录。生产报告不得反向解析文本日志获得进程或 verdict。 | `ROOT-003`；保持唯一事实源和 locality。 |
| `DEC-006` | 会话级流归属记录不复用 `_flow_audit` 的 120 秒 TTL 或 4096 条清空策略；它保存全会话首个已证实的进程、PID、原始五元组、disposition、domain 和 TCP 连接代次。owner 无法解析时写 `unknown`，但不得省略流。 | 完整报告不能因观察性缓存清理丢失事实。 |
| `DEC-007` | 报告在 packet threads 全部退出、WinDivert handles 关闭、双 PCAP writers 成功封口后生成；报告生成或原子发布失败使进程非零退出，且不得留下可被 GUI 当成本次成功报告的半文件。 | 保证输入稳定和失败可判定。 |
| `DEC-008` | TCP 按连接代次和方向重组，去除字节相同的重传/重叠，支持乱序；未填补的内部缺口或重叠字节冲突是完整性失败。UDP 不去重，保持每个报文、方向、顺序、时间、长度和哈希。IPv4/IPv6 都使用同一规则。 | `SRC-USER-001`；避免正常重传导致重复内容，也不吞 UDP 的合法重复报文。 |
| `DEC-009` | HTML 内嵌 schema `fakenet.payload-report.v1` 的机器可读载荷清单，payload 只保存一份无损 Base64；十六进制和 UTF-8 文本由该份数据按需产生。捕获内容与进程/域名等不可信字段只能作为文本或安全编码数据插入，禁止 `innerHTML`/脚本解释；报告核心内容不得依赖 CDN 或网络。 | 完整内容、可机械验收与恶意 payload 安全展示。 |
| `DEC-010` | 既有 NBI 作为协议解释层保留并与流关联；完整 payload 区是字节权威结果。旧的 256 字节 RawListener 展示必须明确降为 preview，不能继续以“Data Hexdump”冒充完整数据。 | 兼容既有可读性，同时消除多事实源。 |
| `DEC-011` | 捕获 fatal 时依次执行既有网络/listener/Diverter 清理并关闭 PCAP，保留失败 PCAP 与日志，返回非零，不生成正常 HTML；GUI 没有本次报告时按既有行为打开证据目录并显示明确失败原因。 | `SRC-USER-002` 与 `SRC-REQ-004`；清理不是成功降级。 |
| `DEC-012` | 真实 VM 的捕获完整性验收必须用 NIC 层 `pktmon --comp nics --pkt-size 0` 作为独立观察面，按流重组后与 FakeNet raw PCAP 和 HTML 中的长度/哈希三方比较。不能只用 FakeNet 自己的日志或双 PCAP 相等结论自证。 | 仓库已有 pktmon 验收 seam；Spike 证明内部序号检查不足。 |
| `DEC-013` | 保持 SRS 要求的 raw/converted PCAP 记录、顺序和修改前/后视图不变；捕获时另在会话内存中按 PCAP record ordinal 记录 `logical_packet_id`、`observation_role`（initial/final/inbound）和关联流。报告先按 logical packet 去除同一包的多观察视图，再按 TCP 序号处理网络重传；UDP 只合并同一 logical packet 的 initial/final 视图，不合并两个不同 logical packet。索引记录数/顺序与 PCAP 不一致即完整性失败。 | `SRC-CONV-002`；避免把 NAT 前后观察视图误当两份应用数据，同时不改变既有 PCAP。 |

### `IMP-002` 将捕获覆盖破坏纳入 fail-closed 生命周期

- 现状：主线程只记录 gap，入站线程不测 gap；队列参数读取失败被吞；writer `healthy=True` 会掩盖覆盖风险；fatal 分支仍会调用 `_generate_reports()`。
- 目标行为：
  1. 两个 handle 均设置并回读 queue length=`8192`、time=`2048 ms`、size=`33554432 bytes`，记录 handle 角色和实际值；失败时在处理首包前终止启动。
  2. 两个 recv loop 使用单调时钟计算上一轮处理耗时；`gap_ms >= readback_queue_time_ms` 只登记第一次 fatal，触发既有停止事件。

- 依赖与顺序：`IMP-001` 先完成；本条先于 `IMP-003/004` 的成功报告路径。
- 实施者可裁决：结构化 marker 的具体名称、内部状态字段和 helper 拆分；必须保持一处权威 overall 判定。
- 不允许：仅提高队列值而不回读、只警告后继续、把 gap 阈值写成未经读取的常量、捕获失败后补一份“可能不完整”报告。

### `IMP-003` 建立捕获支持的会话级流与完整载荷模型

- 来源：`SRC-REQ-001`、`SRC-REQ-002`、`SRC-USER-001`、`SRC-CONV-001`、`SRC-CONV-002`、`ROOT-003`、`DEC-005`、`DEC-006`、`DEC-008`、`DEC-013`。
- 允许修改：`fakenet/diverters/diverterbase.py`、`fakenet/diverters/windows.py` 的流归属采集与报告调用；新增 `fakenet` 内聚焦报告/重组模块；复用现有 `dpkt`，对应新增或既有测试。不得修改 egress verdict 的决策结果。
- 现状：`self.nbis` 是报告唯一输入；`_flow_audit` 是会过期的日志去重缓存；不存在捕获关闭后的 TCP/UDP 完整重组。
- 目标行为：
  1. 首次流裁决时一次性形成会话级归属记录，并将正反方向绑定到同一连接/会话；未知 owner 仍保留五元组和 disposition。
  2. 每次写 PCAP 时同步形成 `DEC-013` 的轻量内存观察索引；不得新增热路径磁盘写入。报告模块顺序读取封口 raw PCAP，不依赖 converted PCAP 或文本日志，先用 record ordinal 与 logical packet identity 消除同一包的多观察视图，再按 `DEC-008` 建立 TCP 连接代次、双向 stream 和 UDP datagram。
  3. 每个流、方向和 UDP datagram 均输出稳定 ID、端点、方向、起止时间、字节数、SHA-256、Base64、进程归属与判定；零 payload TCP 流仍输出元数据。
  4. 观察索引与 raw/converted record 数或顺序不一致、内部 gap、冲突 overlap、无法解析的截断 packet 或报告模型写入失败均给出精确错误并回到 `IMP-002` 的 fatal/非零路径，不静默略过。
  5. 不设置 payload 截断上限或会话流清空上限；采用流式读取/临时分片还是内存重组属于纯实现细节，但最终结果、失败边界和清理要求不变。
- 前置条件：capture writers 已成功封口；coverage 与 writer 当前均健康。
- 依赖与顺序：依赖 `IMP-002` 的生命周期顺序；先于 `IMP-004`。
- 实施者可裁决：新增模块和内部类型名称、临时文件布局、TCP 32 位序号归一化算法；临时文件必须位于会话隔离目录并在成功/失败后清理，不能进入最终 ZIP 或仓库。
- 不允许：生产中解析 `PROCESS_FLOW` 文本日志、仅拼接到达顺序、把重传重复计入 payload、把无 owner 的流丢弃、为大数据静默截断。

  6. Export-Logs 导出成功报告或失败诊断证据并写 SHA-256 清单；不得把历史报告误当本次报告。

- 依赖与顺序：依赖 `IMP-002/003`。
- 实施者可裁决：布局、折叠、配色、分页和按需渲染方式；不得改变字节内容、schema 字段或安全插入规则。

出现下列任一事实时，停止实施并回到方案自评/审核，不得现场改方向：

- 关闭同步 console 后同一 266 秒级停顿仍可稳定复现，且证据定位到另一个不同阻塞点。
- 绑定的 WinDivert/pydivert 无法对两类 handle 设置并回读队列参数，且继续保证完整性需要升级驱动或更换捕获 seam。
- raw PCAP 无法在不解析生产文本日志的条件下唯一关联关键流，必须改变流事实产出位置或持久化协议。
- 完整 HTML 在当前五秒停止合同内无法完成，且需要改变“同步生成后退出”的产品边界。
- pktmon 的 NIC 观察面无法与 FakeNet raw PCAP 建立无歧义的流级比较，必须引入其他独立捕获源。
- 用户对“完整内容”新增解密、协议语义解析、非 TCP/UDP 重组或跨会话历史要求。
