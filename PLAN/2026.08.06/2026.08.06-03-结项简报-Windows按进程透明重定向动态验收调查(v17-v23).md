## 1. 一句话结论

重定向功能**本体完全正确**（owner-gate 10,000/10,000、所有连接数据正确改写到 B、engine 零逻辑错误）；调查期间发现并修复了两个真实缺陷（route-guard 锁竞争、ProxyListener SSL 健壮性）；最终残留的线侧 A 泄漏被**确证为 WinDivert 1.3 对"延迟拆链包"的捕获盲区**——diverter 收不到这些包、无法在 diverter 侧修复，且为**无载荷拆链信令、零数据泄漏**。经项目决策，**接受为已知限制，不升级 WinDivert 2.x、不降门禁、不正式提交**。

## 2. 背景与验收门禁

FakeNet-NG 的"按进程透明重定向"是一个 Windows-only、`DomainAllowList` 的可选扩展：将一个唯一可识别的目标 PE 发往某个已审核公网 IPv4 `A` 的 TCP 流量，在包层把目的地址改写为已审核的 on-link RFC1918 IPv4 `B`（端口不变，覆盖所有 TCP 端口）。

VM 动态验收的硬门禁（不可放宽）包括：10,000 条 owner 流全成功、64 并发 burst、**线侧 A=0**（独立 pktmon 捕获为准，重定向后的真实 A 流量不得出现在网卡上）、双 PCAP 一致、DNS 恢复、无运行期 SUSPEND/Traceback/异常。起点（v16/v17）：owner-gate 因 15 分钟 watchdog 早于约 18 分钟的真实完成时间而被误杀，v17 把 watchdog 有界调整为 25 分钟。

## 4. 已验证生效的修复（v20，保留于交付物）

1. **route-guard 锁竞争（泄漏主因）**：`ProcessRedirectRouteGuard.refresh()` 原在 `with self._lock` 内运行 PowerShell 路由检查子进程（`address_refresh_thread` 每 5 秒一次，~2.6 秒），阻塞 recv 线程的每包 `is_current()` → WinDivert 队列溢出 → 目标包直穿到 A。**修复**：子进程移出锁，仅状态交换时短暂持锁。验证：recv 停顿 **130→1**，fail-closed 语义不变。附并发单测 `test_is_current_does_not_block_while_refresh_runs_route_reader`。
2. **ProxyListener SSL 健壮性**：`ProxyListener.py` 行 243 `ssl_remote_sock.recv` 未加 try/except，ambient 遥测（`arc.msn.com`）触发 SSL 失败时上抛成 Traceback，撞 `validate_runtime_log` 禁用子串门禁。**修复**：`wrap_socket`+`recv` 包进 try/except，warning + 优雅返回。验证：**Traceback→0**。附单测 `test_tls_proxy_recv_failure_returns_without_raising`。

> v20 之后 owner-gate 串行路径 wire-A=0、Traceback=0、停顿归零；重定向本体在所有数据承载阶段完全正确。

## 5. 残留问题：WinDivert 1.3 捕获盲区（确证，diverter 不可修）

- **现象**：每次 owner-gate/burst 结束的相变时刻，少数（5–12）**延迟的 OS 清理/重传 FIN/RST** 出现在网卡上（发向 A），触发线侧 A=0 门禁。
- **决定性证据（v22，epoch 精确对齐）**：这些泄漏包在**各自泄漏时刻既无 `A_TEARDOWN`（收包点）也无 `A_DECISION`（engine 决策点）**；而同一端口的更早拆链包 diverter 都收到并正确 `action=DROP reason=normal_close_tombstone`。即 **WinDivert 1.3 没把这些延迟拆链包交给 diverter**。
- **性质**：无载荷 TCP 拆链信令（FIN/RST），发生在连接数据已正常交换并关闭之后，发往隔离网络中的 A（无可达互联网）；**零数据泄漏、零载荷外泄**。
- **被排除的假设**（六轮逐一证伪）：停顿型队列溢出（v20 已修）、每包磁盘 I/O（write_pcap 已 64KB 缓冲）、send/owner 单点慢、吞吐容量不足（稳态容量 ~400 包/秒）、engine 逻辑错误（零）、ProxyListener Traceback（v20 已修）。
- **修复路径可行性（已评估，均不采用）**：
  - 防火墙纵深（block 出向 A）：**不可行**——Windows 防火墙出向规则在 WFP 传输层评估，先于 WinDivert 的 IP 层捕获，会把重定向的原始 SYN 也先挡掉，破坏重定向。
  - WinDivert 1.3→2.x：pydivert 2.1.0 是 **1.3-only 绑定**（`WinDivertOpen` 1.3 签名、捆绑 1.3 DLL/SYS、`WINDIVERT_ADDRESS` 无 2.x 的 Event 字段），2.x 需更换/重写 Python 绑定 + 2.x 驱动 + 重算 manifest/工具链；且该盲区**疑为 WFP 固有局限**，2.x 未必修复。改动大、收益不保证。
  - diverter 侧减少延迟 RST 生成：只能减少、不能消除（被漏抓的 RST 仍泄漏），且触及墓碑/fail-closed 语义。
