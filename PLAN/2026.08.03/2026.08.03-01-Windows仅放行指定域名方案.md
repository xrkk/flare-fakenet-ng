## 1. 背景与问题

FakeNet-NG 当前的 `HostWhiteList`/`HostBlackList` 实际匹配目标 IP，而不是域名。其命中动作控制的是是否重定向到 FakeNet listener；未重定向的数据包会被原样转发，不等同于防火墙的允许或拒绝。

相关现状：

- `fakenet/diverters/diverterbase.py` 使用 `dst_ip` 执行主机名单匹配，并留有 `TODO: Allow domain resolution`。
- `fakenet/diverters/windows.py` 使用 WinDivert 捕获出站 IPv4 包，当前处理后总会调用 `handle.send()` 重注入。
- `fakenet/listeners/DNSListener.py` 当前主要给 A 查询返回 FakeNet 地址，没有选择性真实 DNS 转发和按 TTL 管理的域名/IP 关联。
- 端口、进程和主机黑名单的现有语义是“不要重定向”，可能造成真实外网直通，不能直接复用为安全策略。

因此，只给现有 `HostWhiteList` 增加一次域名解析不能满足“只放行指定域名”：它无法处理 DNS TTL、CNAME、共享 CDN IP、直接 IP、错误 SNI、IPv6、QUIC，以及现有黑名单造成的绕过。

## 2. 目标

Windows 第一版应实现以下行为：

1. 只有经过受控 DNS 解析得到的 `api.deepseek.com` IPv4 地址可作为真实 TCP/443 上游目标。
2. 样本连接不直接放行到真实服务器，而是重定向到本地透明 TLS 中继；中继在 socket 字节流层读取并校验 ClientHello。
3. TLS ClientHello 中的 SNI 必须精确等于 `api.deepseek.com`，校验成功后中继才建立受控上游连接并转发已缓存的 ClientHello。
4. FakeNet 自身只允许通过预登记的精确 socket 五元组访问指定上游 DNS 和获准服务器，不能使用进程级白名单获得一般外网权限。
5. 其他可被 FakeNet 处理的 TCP/UDP 流量继续重定向到本地 listener，保留分析能力。
6. 任何因现有端口、进程或主机黑名单而仍指向外部地址的数据包，必须经过最终出站裁决，不得自动直通。
7. IPv6 在构造现有 `WindowsPacketCtx` 前单独识别；仅允许 loopback，其他 IPv6 出站失败关闭，避免触发现有 IPv6 解析缺陷；该扩大捕获对系统服务和队列压力的影响必须在 VM 中验证。
8. 策略异常、DNS 异常、SNI 缺失或解析失败时失败关闭，不临时放宽限制。
9. 功能默认关闭，关闭时不得改变现有 Windows/Linux 行为。

## 3. 非目标

Windows 第一版不包含：

- Linux 实现。
- IPv6 真实放行。
- UDP/443 QUIC 放行或 QUIC Initial 解密。
- DoH、DoT 或应用自带 DNS 的真实放行。
- 通配符域名、子域名自动继承或 URL 路径级策略。
- TLS MITM、HTTP Host/path 检查或 API 请求内容检查。
- 对任意协议提供通用七层出口代理。
- 防御拥有管理员权限、可加载/卸载驱动、停止 FakeNet、修改系统网络配置或执行内核代码的样本。
- 防御能够控制虚拟机上游 DNS、NAT、网关或宿主网络的攻击者。
- 在宿主机执行 FakeNet-NG 或加载 WinDivert 的任何测试。

## 4. 策略定义

本方案中的“只放行域名”定义为：

- 配置值是 hostname `api.deepseek.com`，不是包含 scheme 的 URL。
- 真实出口仅限 TCP/443。
- 必须先获得受控上游 DNS 返回的有效 A 记录，并且记录仍在 TTL 有效期内。
- 新建 TCP 流必须通过 TLS SNI 精确校验。
- 域名比较采用去除末尾点、IDNA 规范化和 ASCII 小写后的精确比较。
- `*.deepseek.com`、`deepseek.com`、`www.deepseek.com` 均不因该规则自动获准。
- 已建立且完成 SNI 校验的流可持续到 FIN、RST 或空闲超时；DNS TTL 到期只阻止新流，不中途破坏已批准连接。
- 样本进程始终只与本地透明 TLS 中继建立连接；只有中继创建的、预登记的精确上游 socket 可以真实出网。

该定义仍不是密码学意义上的完整 URL 隔离。TLS SNI 获准后，TLS 内部的 HTTP Host/path 不可见。若第三方审核要求请求级隔离，应另立 TLS MITM/显式代理方案，不得在本方案中隐式扩大范围。

### 4.1 威胁模型与信任边界

本方案只在以下前提成立时提供出口约束：

- FakeNet-NG 进程、配置文件、WinDivert 驱动和测试 VM 管理面可信。
- 被分析样本不能停止/注入 FakeNet，不能修改驱动或防火墙，不能加载内核代码，不能取得与 VM 管理员等价的控制权。
- VM 的上游 DNS、默认网关、NAT 和宿主网络路径可信，不主动伪造 DNS 响应或路由。
- 允许域名本身及其服务端是用户有意授权的真实数据接收方。

本方案不能阻止样本把任意数据发送给已经允许的 `api.deepseek.com`，也不能在不解密 TLS 的情况下限制 HTTP Host、路径、Header、请求体、API Key 使用或费用。若样本可能取得管理员/内核权限，必须改用 VM 外部的强制网关/防火墙实施相同策略，不能依赖 VM 内 FakeNet 自身。

## 5. 建议配置

在 `[Diverter]` 增加默认关闭的选项：

```ini
# Disabled | DomainAllowList
ExternalAccessPolicy:       Disabled

# 仅在 DomainAllowList 模式生效；只接受 hostname
ExternalAllowedDomains:     api.deepseek.com
ExternalAllowedTCPPorts:    443

# Auto 表示在 ModifyLocalDNS 前保存虚拟机原 DNS；也允许明确填写 IPv4
ExternalDnsServer:          Auto
ExternalDnsTimeout:         3

ExternalVerifyTLSSNI:       Yes
ExternalRelayPort:          38927
ExternalTLSHelloTimeout:    5
ExternalTLSHelloMaxBytes:   65536
ExternalMaxPendingFlows:    256
ExternalMaxPendingPerSource: 32
ExternalMaxActiveRelays:    128
ExternalMaxActivePerSource: 16
ExternalRelayIdleTimeout:   300
ExternalRelayBufferBytes:   1048576

# Divert | Drop；建议初始值为 Divert，以保留 FakeNet 分析能力
ExternalNonAllowedAction:   Divert

# Windows 第一版必须保持为 Yes
ExternalBlockExternalIPv6:  Yes
ExternalBlockQUIC:          Yes
```

配置校验规则：

- `DomainAllowList` 必须同时配置非空域名、TCP 端口和上游 DNS。
- 域名项包含 scheme、路径、端口、空白标签或通配符时启动失败。
- 第一版若配置 UDP 真实出口、IPv6 放行或关闭 SNI 校验，应启动失败，而不是静默降级。
- `ExternalDnsServer: Auto` 无法获得可用的、非本机的原 DNS 时启动失败，不自动改用公共 DNS。
- `ExternalRelayPort` 必须为本机未占用 TCP 端口，不能与现有 listener 或默认 listener 端口冲突。
- TLS ClientHello 最大缓存固定为 65,536 字节、等待时间 5 秒、全局 pending 流 256、单来源 pending 流 32；超过任一限制即拒绝连接，不能动态扩容。
- 已批准中继全局最多 128、单来源最多 16，双向空闲 300 秒后关闭，每方向待发送缓存最多 1 MiB；listener 必须在创建工作线程前获取配额，不能先无限创建线程再检查。
- 现有 `HostBlackList`、`ProcessBlackList`、`BlackListPortsTCP/UDP` 仍可影响 FakeNet 重定向，但不能越过最终出站裁决。

## 6. 总体架构

新增一个不依赖 WinDivert 的纯 Python 策略组件 `fakenet/diverters/egresspolicy.py`，由 Diverter 持有，并通过受限 callback 暴露给 DNS listener 和新的透明 TLS 中继 `DomainEgressRelay`。

策略与中继共同维护五类状态：

1. 域名规则：规范化域名及允许端口。
2. DNS lease：`domain -> IP -> expires_at`，使用单调时钟和 DNS TTL。
3. 原始目标映射：按样本侧 `(协议, 源 IP, 源端口)` 保存原目标 IP、端口、域名 lease 和短期有效期，供本地中继查询。
4. 内部控制流许可：FakeNet 内部 socket 在 `bind()` 后、`connect()/send()` 前登记精确五元组和一次性 token；关闭或超时后立即撤销。
5. 中继状态：由 `DomainEgressRelay` 在 socket 流层维护 pending/allowed/denied 状态，不在 WinDivert 数据包层重组 TCP。
6. 专用透明中继 NAT 映射：以完整正向/反向 TCP 五元组和连接代次标识为键，记录原服务器 IPv4/443、本地中继端点、创建时间和状态；不与 FTP 等现有通用转发表共享生命周期。

出站裁决结果固定为：

- `REDIRECT_TLS_RELAY`：样本目标 IP 和端口满足 DNS lease，将连接改写到本地 TLS 中继。
- `ALLOW_INTERNAL_UPSTREAM`：已预登记的中继或 DNS socket 精确五元组，按 `kind=dns|tls_relay` 允许真实外网。
- `DIVERT_FAKE`：已安全改写到本地 FakeNet listener。
- `REINJECT_LOCAL`：返回 NAT 修复已经完成，且目标精确等于 IPv4/IPv6 loopback、本机活动适配器地址，或命中 DHCP 精确例外；原样重注入。该结果不包含“同一子网”“局域网地址”或任意广播/组播。
- `DROP_EXTERNAL`：其他仍指向外部地址的数据包。

裁决结果由单一最终判定函数生成。`check_should_ignore()`、端口/进程/主机名单以及 FTP Active 兼容逻辑只能决定是否执行 FakeNet 改写，均无权直接产生真实出口许可；其结果必须继续进入最终判定。

真实服务器只看到 FakeNet 中继创建的 TCP 连接；样本创建的 socket 不直接离开 VM。中继只解析 ClientHello，不终止 TLS，后续字节原样双向转发，因此客户端仍直接验证真实服务器证书。

## 7. DNS 处理设计

### 7.1 允许域名

收到 `api.deepseek.com` 的 A 查询时：

1. DNS listener 先确认请求来源是本机 loopback 或 FakeNet 已知的本机适配器地址；其他来源直接拒绝，不能成为局域网开放解析器。
2. DNS listener 通过专用 socket 向唯一配置的上游 DNS 发送重新编码的等价查询，不调用系统解析器，避免递归进入 FakeNet；上游查询使用密码学安全随机的独立 transaction ID，并保留客户端原 ID 供合成响应恢复。
3. 先根据上游目标路由选择具体本机源 IPv4，再让专用 socket 显式 `bind((source_ip, 0))` 获得临时源端口；不得绑定 `0.0.0.0` 后猜测源地址。
4. 登记 `(协议, 本地源 IP, 源端口, 上游 DNS IP, 53)` 和仅供内部注册 API 使用的一次性 token，最后才执行 `send()/connect()`；完成、失败或超时后立即撤销。
5. 上游流量必须命中尚未过期的精确控制流许可；不能仅凭 `python.exe`、FakeNet PID 或目标端口 53 放行。
6. 校验响应来源地址、端口、上游随机 transaction ID、QR、问题名称和问题类型；不得用客户端原 ID 校验上游响应。
7. 验证 CNAME 链从允许域名开始，拒绝无关 owner name 和 additional section 注入的 A 记录。
8. 提取最终 IPv4 A 记录；拒绝 loopback、link-local、multicast、unspecified、私网和其他非全局地址。lease TTL 取完整 CNAME→A 链上相关 RR TTL 的最小值。
9. 不把上游原始包直接返回客户端，而是恢复客户端原 transaction ID，并用原 question 和验证后的 CNAME/A 记录合成最小响应，清除 AD/DNSSEC 声明及无关 additional 数据；v2 明确不提供 DNSSEC 验证。
10. 若合成后无有效 A，返回 SERVFAIL；一次新的成功解析应原子替换该域名用于新连接的旧 IP 集合，而不是把历次地址无限合并。
11. 先将有效记录原子地登记到策略缓存，再将合成响应发给请求进程，消除“客户端已连接但策略尚未更新”的竞态。
12. TTL 为 0 的地址不创建可用于新连接的 lease。

若响应只有 CNAME 而没有终端 A 记录，可临时登记该 CNAME 为原允许域名的解析别名，仅允许继续向同一上游 DNS 查询该别名；别名本身不成为新的出口域名规则。

上游 DNS 使用普通 DNS，因此 v2 明确信任 VM 网络和所选解析器，不声称抵抗 DNS 路径上的主动篡改。测试 VM 必须在测试前已经配置审核认可的 DNS IPv4；一键测试运行器从首选默认路由对应的已连接接口自动选取该现有配置，并把结果写入本次临时运行配置，不要求操作者输入，也不会发明公共 DNS fallback。

### 7.2 其他域名

非允许域名继续使用现有 FakeNet 假 DNS 响应，以保留恶意样本行为分析能力；其后续连接应被改写到本地 listener，而不是真实外网。

### 7.3 AAAA 与其他类型

- 第一版对允许域名的 AAAA 返回 NOERROR/NODATA，不登记 IPv6 lease。
- MX、TXT 等查询不产生真实出口授权。
- HTTPS/SVCB 记录不产生真实出口授权。
- DNS 超时、截断处理失败、格式错误、无有效 A 记录时返回 SERVFAIL，并保持失败关闭。
- 同时提供本机 UDP/53 和 TCP/53 DNS listener；样本侧 TCP DNS 与上游 TC→TCP fallback 都必须经过相同的域名、响应和控制流校验。

## 8. Windows 数据包处理设计

### 8.1 捕获范围

`DomainAllowList` 模式下，WinDivert filter 应覆盖 outbound IPv4 和 IPv6，但不得把 IPv6 交给现有 `WindowsPacketCtx`。接收后先检查 WinDivert packet 元数据或原始 IP version nibble：loopback IPv6 原样重注入；其他 IPv6 记录原因后丢弃。该预处理必须没有地址改写和 dpkt IPv6 依赖。VM 前置测试必须验证 pydivert 对纯 IPv6 包 `send()` 时的解析和校验和行为；若当前版本无法安全重注入 loopback IPv6，则本功能不得验收，不能未经复审自行改为宽泛 IPv6 放行。

常规模式继续使用原有 filter，避免默认行为回归。

WinDivert handle 不得在 `Diverter.__init__()` 中打开。v2 要求把 handle 创建、`open()` 和接收线程启动推迟到策略、listener、callback、上游 DNS 选择和配置校验全部就绪之后；启动失败时不得留下已经捕获但无人处理的数据包。

### 8.2 处理顺序

每个出站包按以下顺序处理；步骤顺序属于安全约束，不得由实现者重排：

1. `classify_ipv6_preparse(raw_packet) -> REINJECT_LOCAL | DROP_EXTERNAL | NOT_IPV6` 在构造 `WindowsPacketCtx` 前处理 IPv6；外部 IPv6 失败关闭，只有明确的 loopback IPv6 可重注入。
2. 对 IPv4 保存原始五元组、PID、进程名和原始目标地址，由 `capture_original_once(pkt)` 恰好写入一次原始包。策略模式调用现有 `handle_pkt()` 时传入 `raw_already_captured=True`（或等价的单一捕获协调器），禁止再次写同一原始包；仅在发生改写时额外写一次带明确标记的改写后包。
3. `match_internal_upstream(original_5tuple) -> Optional[ControlPermit]` 判断是否命中尚未过期的 FakeNet 内部精确控制流。只有已按具体路由源 IPv4 执行 `bind()` 的 DNS socket 和 SNI 已验证中继 upstream socket 可以获得该许可；一次性 token 只授权内部代码创建许可，数据包仍按完整五元组匹配。命中后跳过 FakeNet 改写，在最终裁决中只能得到 `ALLOW_INTERNAL_UPSTREAM`。
4. 对未命中控制流的包调用 `apply_domain_relay_return_fixup(pkt) -> bool`。函数必须独立于 `handle_pkt()` 和 cb4，在最终裁决之前执行；仅当专用反向五元组和连接代次精确命中时，才把中继源 IP/端口恢复为原服务器 IPv4/443。该函数对 loopback 包同样执行；“执行函数”不等于无条件改写，未命中时不得改变包。
5. 对样本到服务器方向先调用 `apply_domain_relay_forward_redirect(pkt) -> bool`：已有活动映射精确命中时，把该 TCP 流的每个后续包继续定向到同一本地 relay 端点。未命中且原始目标为有效 DNS lease 对应的 IPv4 TCP/443、新 SYN 可建立映射时，才调用 `redirect_domain_tls_syn(pkt, lease) -> RelayNatMapping`，以一次原子操作建立正向改写、反向修复、一次性原始目标映射和连接代次，再把 SYN 改写到本机 `DomainEgressRelay`。非 SYN 不得凭 lease 补建映射；任何状态不能完整建立时删除本次状态并丢弃，不能半重定向或直连。
6. 其他 TCP/UDP 包执行现有 `handle_pkt()`，使其有机会被重定向到 FakeNet；它的 ignore/blacklist 结果不能结束策略路径。FTP Active 端口兼容逻辑保留原功能，但不能授予出口。
7. 调用唯一的 `finalize_egress_verdict(pkt, context) -> Verdict`：
   - 第 3 步精确许可仍有效：`ALLOW_INTERNAL_UPSTREAM`，按原始外部目标重注入；
   - 第 5 步已完整改写到 TLS 中继，或现有逻辑已安全改写到已启动的本机 FakeNet listener：`REDIRECT_TLS_RELAY` / `DIVERT_FAKE`，重注入；
   - 第 4 步已完成返回修复，且目标精确等于 loopback 或当前本机活动适配器 IP：`REINJECT_LOCAL`，重注入；
   - 未经 NAT 修复但目标精确等于 loopback 或当前本机活动适配器 IP：`REINJECT_LOCAL`，重注入；这不扩展为同子网、RFC1918、任意广播或组播许可；
   - 精确匹配 IPv4 DHCP UDP 68→67 且目的为规定的广播地址：`REINJECT_LOCAL`；
   - 其余仍为外部地址、UDP/443、未知协议、异常或无法分类：`DROP_EXTERNAL`，不调用 `handle.send()`。

```python
if ipv6_verdict != NOT_IPV6:
    return enforce(ipv6_verdict)
ctx = capture_original_once(WindowsPacketCtx(raw))
if permit := match_internal_upstream(ctx.original_5tuple):
    return enforce(finalize_egress_verdict(ctx, permit=permit))
fixed = apply_domain_relay_return_fixup(ctx)
forwarded = False if fixed else apply_domain_relay_forward_redirect(ctx)
if not fixed and not forwarded and is_new_allowed_tls_syn(ctx):
    mapping = redirect_domain_tls_syn(ctx, current_lease(ctx))
elif not fixed and not forwarded:
    handle_pkt(ctx, raw_already_captured=True)
return enforce(finalize_egress_verdict(ctx))
```

对进入现有 `handle_pkt()` 的包，最终裁决必须位于其后；精确内部控制流则按步骤 3 直接进入同一个最终判定函数。这样确保 `BlackListPorts`、`ProcessBlackList` 和 `HostBlackList` 的“不要重定向”语义不会等同于“允许真实外网”。

TLS 中继定向可抽取现有 `ip_fwd_table`、`port_fwd_table` 的改写原语，但必须使用专用 `RelayNatTable` 管理状态，避免与既有 FakeNet/FTP 映射共享生命周期。映射只在新 SYN 上创建，以正向和反向完整五元组及单调递增的连接代次区分；活动映射不得被同端口的新包覆盖。中继关闭、FIN/RST、握手超时或映射硬 TTL 到期时原子撤销双向表项和原始目标映射。源端口复用只有在旧代次已关闭并设置短期 tombstone 后才能创建新代次；旧代次迟到包不得命中新映射。映射缺失或冲突时丢弃 SYN，不允许直连。

### 8.3 必要的本地控制流

以下流量不属于真实互联网出口，可按精确规则保留：

- IPv4/IPv6 loopback 和目标为 FakeNet 本机 listener 的流量。
- DHCP IPv4 广播 UDP 68→67；只允许协议、端口和广播地址完全匹配的报文。

其他局域网、广播和组播流量不得因为“不是互联网域名”而自动放行；应进入 FakeNet 或丢弃。

## 9. 透明 TLS 中继与 SNI 校验

仅凭 DNS 产生的 IP lease 会允许同一 CDN IP 上的其他域名，因此样本 TCP/443 连接统一重定向到本地 `DomainEgressRelay`。SNI 解析在操作系统已经重组好的 TCP socket 字节流中完成，不在 WinDivert 层缓存或重注入 TCP 分片。

流程：

1. 中继接受本地连接后，用客户端源 IP/端口向策略 callback 查询专用原始目标映射；不存在、过期、已消费或不是有效 DNS lease 时立即拒绝。
2. 在 5 秒内最多读取 65,536 字节，解析单个完整 TLS ClientHello；一旦已读前缀足以证明不是 TLS ClientHello，应立即拒绝，不等待上限。全局最多 256 个 pending 流，同一来源最多 32 个，并对同一来源的连续拒绝和新建速率限流。
3. SNI 规范化后必须精确等于映射中的 `api.deepseek.com`。SNI 缺失、不匹配、检测到 ECH 扩展、非 TLS、畸形 ClientHello或资源上限均关闭连接，不建立任何上游 socket；不能因为 outer SNI 匹配而接受 ECH。
4. 校验成功后，中继按原目标路由选出具体本机源 IPv4，创建上游 TCP socket 并显式 `bind((source_ip, 0))`，登记精确五元组和一次性内部注册 token，再连接原始目标 IPv4/443。
5. 上游连接成功后，将截至解析成功时已经从客户端读取的**全部字节**按原顺序转发，包括完整 ClientHello 以及同一读取缓冲中其后的 TLS 1.3 0-RTT 或其他 TLS records；不得只截取 ClientHello。随后进入有界双向 relay；TLS 不在 FakeNet 终止，客户端仍验证真实服务器证书。
6. 任一方向 EOF、FIN/RST、异常、300 秒双向空闲或中继停止时，立即关闭两端 socket、撤销控制流和原始目标映射。全局 active 中继最多 128、单来源最多 16，每方向待发送缓存最多 1 MiB。

中继不得接受调用方提供的任意上游地址，必须只使用 Diverter 在重定向前记录且仍有有效 lease 的原目标。直接连接本地中继端口但没有一次性原始目标映射的请求必须失败。

中继在第一版只绑定一个 IPv4 `0.0.0.0:<ExternalRelayPort>` 监听 socket，以同时覆盖 Windows 的 loopback 和非 loopback 本机地址。具体重定向地址继续采用已核实的 `WinUtilMixin.getNewDestinationIp(src_ip)` 规则：`127/8` 来源定向到 loopback，其他本机 IPv4 来源定向到当前 `external_ip`。accept 后必须先确认客户端源地址属于 loopback 或当前本机地址集合，再用完整源端点和连接代次消费映射；任一校验失败立即关闭。第一版不创建 IPv6 中继监听。

该设计消除了 v0 在 WinDivert 层处理 TCP 分片、乱序、重传和延迟重注入的高风险，但仍不能检查 TLS 内的 HTTP Host/path，也不能阻止获准服务成为数据接收方。

## 10. 启动顺序与接口

当前 `fakenet.py` 在 listener 已启动后先启动 Diverter，随后才注入 callback，存在短暂竞态；Windows Diverter 还在构造函数中提前打开 WinDivert handle。v2 采用受配置保护的 Windows 两阶段启动，不全局改变 Linux 和普通模式：

1. 构造 Windows Diverter，但只完成纯配置、地址和策略初始化，不创建/打开 WinDivert handle，不修改 DNS。
2. 只构造普通 listener、UDP/TCP DNS listener 和 `DomainEgressRelay` 对象，不绑定端口、不启动线程。相关 provider 增加构造期安全的 `configure_dependencies(listeners, diverter_view, callbacks)`，只把依赖保存到 provider 字段，不访问尚不存在的 `self.server`。
3. 通过 `configure_dependencies(...)` 注入完整 listener 列表、只读 Diverter 视图和受限 callback；选择并验证上游 DNS，保存待恢复的系统 DNS 信息，并执行 ready 自检。listener 的 `start()` 创建 `self.server` 时必须在启动 `serve_forever` 线程之前把已保存依赖赋给 server；不得继续依赖现有“start 后才调用 `accept*`”的竞态接口。
4. callback 和配置全部 ready 后，才让 listener 绑定端口并启动线程；任何 listener 启动失败都停止已启动对象并退出。
5. listener 全部 ready 后才调用 Windows Diverter 的 `start()`：打开 WinDivert并立即启动接收线程，确认线程存活后再修改本机 DNS和刷新缓存。
6. 接收线程必须有 watchdog；若线程意外退出，立即停止接收新样本连接、关闭 WinDivert handle并恢复 DNS，保持失败可见，不能切换为兼容放行。
7. 任一步失败都按逆序停止已启动 listener、关闭 handle并恢复 DNS；不得进入无策略的兼容放行模式。

运行时停止顺序要求测试控制器先终止被分析样本，再停止 listener/中继，撤销内部控制流，恢复 DNS，最后关闭 WinDivert handle。若无法保证先停止样本，应先隔离 VM 虚拟网卡，再执行恢复，避免退出窗口产生真实流量泄漏。

普通 Windows 模式和 Linux 继续使用原启动路径。若实现发现无法在不复制大量逻辑的情况下安全限定该顺序，必须先单独重构 listener 生命周期并补齐全平台回归测试，不能把未经验证的全局重排混入本功能。

DNS callback 只暴露所需能力：

- 查询域名是否允许真实解析。
- 登记/撤销 DNS lease 和 CNAME 解析别名。
- 创建、消费和撤销样本连接的原始目标映射。
- 登记/撤销上游 DNS 与 TLS 中继 socket 的精确临时控制流。
- 记录 DNS 和出口策略审计事件。

不得把完整 Diverter 或可任意添加出口许可的可变容器直接暴露给 listener。

包处理热路径只能读取不可变地址快照，并对预分配/有界哈希表做 O(1) 查询或短临界区原子更新；禁止在 WinDivert 接收线程内执行 DNS、socket I/O、等待 relay、磁盘同步写或获取可能被 DNS/中继线程长期持有的锁。地址/路由热变更通过新快照发布；发布或查表异常均失败关闭。

## 13. 未显式确认的 fallback

以下 fallback/退化行为是方案为安全性和兼容性主动加入的，尚未得到项目负责人逐项确认，第三方审核和实施授权前必须明确处理：

1. **非允许流量优先重定向，无法确认已安全重定向时丢弃。** `ExternalNonAllowedAction: Divert` 保留 FakeNet 分析能力；若包经现有逻辑处理后仍指向外部地址，最终裁决 fallback 为 `DROP_EXTERNAL`。
2. **DNS UDP 截断时改用同一上游 DNS 的 TCP/53。** 仅当响应设置 TC 位时启用，不改用其他 DNS 服务器；TCP 失败后返回 SERVFAIL。
3. **DNS/SNI/策略异常统一失败关闭。** 不使用旧缓存、不直接放行 IP、不临时关闭 SNI 校验。
4. **AAAA/外部 IPv6 退化为不提供真实地址并阻断。** IPv6 必须在进入现有 PacketCtx 前裁决；loopback IPv6 保留，不 fallback 到真实 IPv6。
5. **QUIC 被阻断后客户端可能自行回退到 TCP/443。** 这只是客户端兼容预期，不是 FakeNet 提供或保证的 fallback；若客户端不回退，连接失败。
6. **客户端证书撤销查询被阻断时不自动放行 OCSP/CRL/AIA 域名。** VM 验收使用不依赖额外外网的客户端配置；如必须放行证书附属域名，应修订域名规则并重新审核。
7. **listener 未正常绑定时退化为丢弃。** `ExternalNonAllowedAction: Divert` 依赖目标 listener 已 ready；listener 缺失、端口冲突或状态不一致时不尝试直连，统一 `DROP_EXTERNAL` 并使启动/健康检查失败。

明确不允许的隐式 fallback：

- 原 DNS 不可用时改用 `8.8.8.8`、`1.1.1.1` 或其他公共 DNS。
- SNI 缺失时仅凭 IP lease 放行。
- DNS 响应无有效 TTL 时赋予自定义长期 TTL。
- WinDivert/SNI parser 异常时恢复当前“所有包重注入”的行为。
- 为解决 HTTPS 验证失败而自动放行代理、OCSP、CRL、AIA、DoH 或重定向域名。

## 14. 第三方审核重点

第三方审核应至少覆盖以下项目，并形成逐项结论：

### 14.1 安全边界

- 威胁模型是否明确排除了管理员/内核级样本，部署环境是否满足该前提。
- 是否存在任何路径可绕过最终出站裁决并调用 `handle.send()`。
- 现有端口、进程、主机黑名单是否仍可能造成真实外网直通。
- FTP Active 兼容 hack 在目标为本机时是否保持既有行为，同时其 ignore 结果是否必然继续经过最终裁决；不得把该 hack 的本机触发条件误判为外部 upstream 的直接许可。
- FakeNet 内部 socket 是否只能通过精确、短期、一次性的五元组许可出网，其他 Python/FakeNet 线程能否滥用许可。
- DHCP、本地 listener 和控制流例外是否足够精确，是否允许局域网横向访问。
- DNS 和 TLS 中继是否拒绝非本机来源以及没有原始目标映射的本地直连。

### 14.2 DNS 正确性与攻击面

- transaction ID、响应来源、qname/qtype、CNAME 链和 owner name 校验是否完整。
- DNS rebinding、多 A、短 TTL、TTL=0、CNAME 循环、TC/TCP fallback 是否安全。
- DNS lease 是否在发送响应给客户端前原子登记。
- 是否可能通过伪造 additional section 给任意 IP 建立 lease。
- `Auto` 上游 DNS 选择是否可能选到 FakeNet 自身或不可路由地址。

### 14.3 TLS 中继和 socket 生命周期

- ClientHello 是否只在本地 socket 字节流中解析，是否完全移除了 WinDivert 层分片缓存/重注入。
- 中继是否在 SNI 校验前保持没有任何真实上游 socket，校验后是否只连接保存的原目标。
- SNI 缺失、ECH、畸形扩展和大小上限是否失败关闭。
- 原始目标映射是否一次性消费、绑定客户端源端点并及时过期。
- 专用 NAT 表是否按正反五元组和连接代次原子建立/撤销，FIN/RST、relay 关闭、超时及源端口复用时是否不会误修复迟到包。
- 上游 socket 是否在 `connect()` 前登记精确控制流，失败和关闭后是否必然撤销。
- pending/relay 流是否有明确的数量、字节、空闲和时间上限。
- ClientHello 解析完成时已经读取的后续 0-RTT/records 是否全部按原序转发；明显非 TLS 是否尽早拒绝。

### 14.4 IPv6 与其他协议

- WinDivert filter 是否确实捕获 IPv6，确保第一版阻断而不是旁路。
- IPv6 是否在构造当前 `WindowsPacketCtx` 前裁决，避免 `inet_ntoa()` 解析 IPv6 的异常路径。
- UDP/443、DoH、DoT、ICMP、未知 IP 协议和直接 IP 是否均不能真实出网。
- loopback、FakeNet listener 响应和真实连接返回流量是否不会被误阻断。
- pydivert 当前实际版本的 IPv6 loopback 重注入和校验和行为是否在 VM 中验证；不得靠禁用 IPv6 跳过该安全测试。

### 14.5 生命周期与恢复

- 正常退出、异常退出、线程异常时 DNS 设置和 WinDivert handle 的恢复行为。
- WinDivert handle 是否只在所有策略依赖 ready 后打开，初始化失败是否会留下无人接收的捕获队列。
- 策略缓存是否在启动、停止和配置切换时清空。
- listener callback 注入和 Diverter 启动顺序是否消除竞态且不破坏现有 listener。
- `configure_dependencies()` 是否在 `self.server` 创建前安全保存依赖，并在工作线程启动前完成 server 注入。
- 日志和 PCAP 是否会泄露认证信息，拒绝日志是否具备限速。
- 原始/改写后 PCAP 是否各自至多写一次；WinDivert 热路径是否无网络 I/O、无长期锁等待并能承受扩大后的捕获压力。

### 14.6 兼容性与范围控制

- 功能关闭时是否保持现有行为和配置兼容性。
- 实施是否引入未批准的第三方依赖、驱动变更或证书行为。
- 是否准确声明“域名+SNI级”而没有误称为完整 URL/HTTP 请求级隔离。
- 是否记录允许域名本身仍可接收任意数据、普通 DNS 路径受信任等残余风险。

## 15. 测试约束

### 15.1 环境约束

- 仅在具备快照的隔离 Windows 虚拟机中运行。
- VM 不包含宿主机凭据、代理凭据、共享剪贴板敏感数据或宿主机可写共享目录。
- FakeNet-NG、WinDivert、DNS 修改和所有网络测试都只在 VM 内执行。
- 测试前创建快照，测试后停止 FakeNet、验证 DNS 恢复，并保留 VM 内日志和 PCAP。
- 启动 FakeNet 前校准 VM 时间、禁用系统/环境 HTTP 代理、确认测试命令不携带 API Key，并确保 VM 首选默认路由所在接口已经配置审核认可的上游 DNS IPv4；运行器自动读取并固化该值。
- VM 内使用独立抓包工具观察虚拟网卡；FakeNet 自身 outbound PCAP 只作为补充证据，不能替代完整链路抓包。
- 宿主机只允许进行离线代码审阅和文档编辑，不得启动该工具。
- 安全验收阶段保持 VM IPv6 启用，用于证明外部 IPv6 被捕获并丢弃、loopback IPv6 可安全重注入。可在该阶段之后另做“禁用 IPv6”的稳定性对照，但对照结果不能替代 IPv6 安全验收。
- 预期策略会截断 VM 中 Windows Update、遥测、NTP、NCSI 及分析工具等所有未授权外部流量；测试前应停用非必要联网任务并为 `DROP_EXTERNAL` 日志限速，但不得为减少噪音添加放行规则。

### 15.2 纯策略测试

即使不依赖 WinDivert，以下测试也按本项目约束只在 VM 内运行：

- 域名规范化和精确匹配。
- A/CNAME 解析链、多 A、TTL 到期、TTL=0。
- 伪造响应、错误 transaction ID、无关 additional A、私网地址拒绝。

- IPv4 TCP/443 与其他端口/协议分类。
- 原始目标映射的一次性消费、超时、错误客户端源端点和直接访问中继端口。
- 首个 SYN 与同流后续包的正向 relay 定向、反向源修复、loopback 返回路径、FIN/RST/relay 关闭清理、硬 TTL、同源端口复用、旧代次迟到包和 tombstone。

### 15.3 VM 正向测试

在 VM 中执行：

```powershell
curl.exe --noproxy "*" -v --http1.1 --ssl-no-revoke https://api.deepseek.com/
```

`--ssl-no-revoke` 仅用于避免测试额外访问 OCSP/CRL 域名；它不关闭证书链和 hostname 校验。如果 VM 的 curl 不支持该选项，应使用已确认不需要额外网络的等价客户端，不能改用 `-k/--insecure`。

验收条件：

- 获得受控上游 DNS 的真实 A 记录。
- 日志依次出现 `DNS_LEASE_ADD`、`REDIRECT_TLS_RELAY`、`TLS_SNI_ALLOW` 和 `ALLOW_INTERNAL_UPSTREAM`。
- TLS 证书不是 FakeNet 自签证书，SNI 为 `api.deepseek.com`。
- 获得任意真实 HTTP 响应即可；401、403、404 等不代表网络失败。
- VM 内独立抓包中，样本连接终止于本地中继，真实服务器连接由 FakeNet 进程发起且只使用获准 IP 的 TCP/443。

不得在测试命令或日志中写入真实 DeepSeek API Key。

### 15.4 VM 负向测试

至少覆盖：

```powershell
curl.exe -v https://example.com/
curl.exe -v http://api.deepseek.com/
curl.exe -v https://<deepseek-ip>/
curl.exe -v --resolve example.com:443:<deepseek-ip> https://example.com/
curl.exe -6 -v https://api.deepseek.com/
```

另需验证：

- 未经 DNS lease 的 DeepSeek IP 直连失败。
- 已有 DNS lease 后，直接 IP 因无正确 SNI 仍失败。
- 共享 IP 配合错误 SNI 失败。
- 直接连接本地中继端口且没有原始目标映射时失败。
- 外部 DNS 直连被重定向或丢弃，只有 FakeNet 登记的控制流能访问上游 DNS。
- UDP/443、DoT、DoH 和未知协议不能真实出网。
- `ProcessBlackList`、`HostBlackList`、`BlackListPortsTCP/UDP` 无法造成旁路。
- 未登记的 FakeNet 自身 DNS/TLS socket 即使源端口进入现有 blacklist/FTP Active 兼容路径也不能真实出网；默认 `BlackListPortsUDP: 443` 不能让 QUIC 直通。
- DNS 合成响应、TLS 中继返回包、ICMP 本机响应和精确 DHCP 例外不会被误丢弃；任意同子网/RFC1918/广播/组播目标不会因 `REINJECT_LOCAL` 被泛化放行。
- 策略组件异常、DNS 超时、SNI parser 异常均失败关闭。

## 18. v2 已固定决策与待审核确认

v2 在 v1 内部自评和第三方审计交叉核验后固定以下决策，不再作为实施时的自由选择：

1. 非允许流量先尝试 FakeNet 重定向；最终仍指向外部时必须丢弃。

3. 第一版阻断外部 IPv6、QUIC、DoH 和 DoT；IPv6 loopback 保留。
4. 采用“DNS lease + 本地透明 TLS 中继 + socket 流层 SNI”隔离，不实施 TLS MITM，不声称具备 HTTP 请求级隔离。

6. 允许经过严格 CNAME 链验证的临时解析别名继续查询同一上游 DNS，别名不升级为出口域名规则。
7. ClientHello 上限为 65,536 字节、5 秒；pending 流全局 256、单来源 32，超限失败关闭。
8. 最终裁决增加精确的 `REINJECT_LOCAL`，但不把本地子网、私网、广播或组播泛化为本机流量。
9. 返回 NAT 修复使用专用双向五元组/连接代次表，并在 `handle_pkt`/cb4 之外、最终裁决之前应用；映射未命中不得改写。
10. 既有 FTP Active 兼容 hack 保留，但其 ignore/blacklist 结果不具备出口授权，必须由最终裁决覆盖。
11. 中继绑定单一 IPv4 wildcard socket；依赖通过构造期安全的 `configure_dependencies()` 注入，普通 Windows/Linux 生命周期不变。
12. 上游 DNS 使用独立随机 transaction ID；中继转发解析时已读取的全部字节；PCAP 由单一协调器去重。

第三方仍需明确确认：

1. “不防御管理员/内核级样本、信任 VM 网络和上游 DNS”的威胁模型是否符合部署场景。
2. 允许域名本身可接收任意数据、TLS 内 Host/path 不可见的残余风险是否可接受。
3. VM 测试使用 `--ssl-no-revoke` 避免额外 OCSP/CRL 出口是否可接受。
4. DHCP、loopback、本地 listener 例外是否足够且没有局域网旁路。
5. 精确内部控制流许可、原始目标一次性映射和 Windows 两阶段启动是否具备可实现性和完整回收路径。

## 20. v1 内部自评记录

### 20.1 自评范围

本次自评只检查方案完整性、代码现状适配性、安全边界、兼容性、fallback 和测试可验收性。没有修改实现代码，没有运行 FakeNet-NG，没有加载 WinDivert，也没有从宿主机访问测试域名。

### 20.2 已关闭的 v0 高风险问题

1. **包层 TLS 重组风险：已关闭。** v1 改用本地透明 TCP 中继，在 socket 字节流层解析 ClientHello，不再缓存和重注入 WinDivert TCP 分片。
2. **IPv6 解析崩溃路径：方案层已关闭。** v1 要求 IPv6 在构造现有 `WindowsPacketCtx` 前裁决，避免把 16 字节地址交给 `inet_ntoa()`。
3. **WinDivert 提前打开：方案层已关闭。** handle 延迟到 listener、callback、策略和 DNS 全部 ready 后打开，并增加接收线程 watchdog。
4. **callback 注入竞态：方案层已关闭。** v1 明确采用“只构造→注入依赖→绑定/启动 listener→启动 Diverter”的策略模式两阶段生命周期。
5. **DNS开放解析器：方案层已关闭。** DNS listener 必须验证本机来源，非本机请求不得进入真实解析或 lease 更新。
6. **进程级宽泛放行：已关闭。** DNS和TLS上游均使用具体源 IPv4、完整五元组、短期许可和内部一次性注册 token，不使用 `python.exe`/PID 白名单。
7. **DNS additional 注入和TTL链：已关闭。** v1 合成最小响应、过滤无关记录、取CNAME→A链最小TTL，并原子替换新连接使用的地址集合。
8. **PCAP验收不完整：已关闭。** 完整链路证据改由VM内独立抓包提供，FakeNet outbound PCAP只作补充。
9. **双向重定向遗漏：已关闭。** v1要求TLS中继定向原子建立原始目标、IP修复和端口修复状态，无法完整建立时丢弃SYN。

“方案层已关闭”只表示文档已经给出唯一处理要求；是否正确实现仍需代码审核和VM测试证明。

### 21.1 已纳入的审计结论

| 审计项 | v2 处理 | 纳入原因 |
|---|---|---|

### 21.2 未照单全收的审计表述

1. 不接受“B3 会直接作用于未登记的外部 DNS/TLS upstream socket”的事实判断。当前 hack 还要求源、目的地址都属于本机非 loopback；普通 upstream 包的目的地址是外部 DNS/服务器，不满足条件。v2 接受其背后的防纵深要求，但不禁用 FTP 兼容机制。
2. 不接受“B1 必然导致 DNS 响应被丢弃”的确定性表述。v1 只明确外部目标丢弃，本机非 listener 流量属于未定义而非已定义为丢弃；该歧义本身仍足以构成必须修订的问题。
3. 不接受把“测试前禁用 IPv6”作为安全验收前置条件，因为这会掩盖扩大 filter 后的 IPv6 捕获/丢弃旁路。v2 先在启用 IPv6 时做安全验收，之后可另做禁用 IPv6 的稳定性对照。
4. 不接受对所有非控制流数据包“无条件修复 NAT”的字面要求。正确约束是无条件到达专用修复判定点，但只有精确反向映射命中才能改写；否则会破坏普通本地流量。

## 23. v4 一键测试交互修正

### 23.1 根因与修正

### 30.2 根因与修正

Windows 既有 `getNewDestinationIp()` 对任何非 loopback 源地址都返回单一 `Diverter.external_ip`。该字段在多网卡 VM 中可能由适配器枚举顺序选为与当前流不同的接口地址。本轮样本从 `192.168.204.166` 发起，但 relay 目标被选为 `192.168.243.129`；重注入包因跨本机接口再次被 WinDivert 捕获，并作为普通本地 listener 流进入 FakeNet，未到达域名中继 accept 路径。

`DomainEgressRelay` 已按审核方案绑定单一 IPv4 wildcard socket，因此 v11 对获得有效 DNS lease 的新 SYN，直接使用包的原始本机源 IPv4 作为 relay 目标。`EgressPolicy.create_relay_mapping()` 仍会验证样本源和 relay 目标都是当前本机精确地址，relay 端口仍必须等于审核值 `38927`。新增 Windows 裁决单元测试模拟 `external_ip` 属于另一接口，断言映射和改写目标仍使用当前流源地址。

- 风险等级：**中**。修改 Windows 域名中继重定向地址选择，错误会影响正向可用性或本地重注入路径。
- 风险控制：只修改已有有效 lease、TCP/443 新 SYN 的本机目的地址；外部目标、SNI、控制流许可、最终裁决和 wildcard listener 配置均不变。非本机伪造源仍会被 `create_relay_mapping()` 拒绝并失败关闭。
- 超出原方案文件表：没有新增文件；`windows.py` 和 Windows 裁决测试均在原落地范围内。该修改是对方案既定多网卡本机 relay 约束的缺陷修正。
- fallback 评估：没有新增 fallback，也不轮询其他适配器或真实目标；无法建立精确本机映射时仍直接失败关闭。

v11 需要在同一隔离多网卡 VM 复测。预期 Windows 裁决测试总数增加到 9、全部单元测试总数增加到 29，正向连接应产生 `TLS_SNI_ALLOW`，且 PCAP 中真实 TCP/443 必须仍由 FakeNet 中继源端口发往有效 lease 地址。
