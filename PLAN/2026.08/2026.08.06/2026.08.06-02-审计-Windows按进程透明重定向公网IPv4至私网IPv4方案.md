## 0. 总体评价

方案整体工程纪律强、范围边界清晰、风险披露充分、fallback 声明严谨，§22 内部自评已主动修正了 SubIfIdx、生命周期、分片、事务、PE 客户端等关键问题。逐条核实后，方案对**现有代码基线的描述全部准确**（见 §1），但在以下三处存在实质问题，必须升版处理：

| 编号 | 级别 | 问题 | 影响 |
|---|---|---|---|
| M1 | 严重（事实错误） | 方案通篇称 WinDivert 1.1.8；实际运行时驱动为 **1.3.0**（经 `pydivert==2.1.0` 自带 DLL 加载，服务名 `WinDivert1.3`），仓库 `windivert/` 下的 1.1.8 二进制在运行时从不被加载 | 动摇"是否必须升级驱动才能取得可靠身份"的可行性论证基础；首 SYN owner 门禁必须在真实 1.3.0 行为下重做 |

## 2. 必须修正的问题（M1–M3）

### M1（严重·事实错误）WinDivert 运行时版本为 1.3.0，不是 1.1.8

**方案主张（多处）：**
- §3.4（L130）"仓库内 WinDivert 驱动版本为 1.1.8"
- §5.4（隐含）"WinDivert 1.1.8 下首 SYN owner 是否稳定"
- §17/§18 风险与审核重点
- §21.0/§22.6.1（L770、L1288）"WinDivert 1.1.8"

**实际情况（已逐项核实）：**

1. 仓库 `windivert/` 目录确实存放 1.1.x 系列 DLL/SYS（`WinDivert64.dll` 15872 B、`WinDivert64.sys` 38064 B），且 `fakenet.spec:26,32` 将其打包进 EXE——**但这些二进制在运行时从不被加载**。
2. `pydivert==2.1.0`（锁文件 `requirements-domain-takeover-windows.lock:16` 固定，hash `382db488...`，与 `wheelhouse/pydivert-2.1.0-py2.py3-none-any.whl` 一致）自带 WinDivert **1.3.0** 二进制（其包内 `WinDivert64.dll` 22528 B、`WinDivert64.sys` 47560 B，与仓库 1.1.x 字节数完全不同）。
3. `pydivert/windivert_dll/__init__.py` 计算 `here = os.path.dirname(__file__)` 后 `DLL_PATH = os.path.join(here, "WinDivert64.dll")`，即**只从 pydivert 自己的包目录加载 DLL**，不从仓库 `windivert/` 加载。其模块 docstring 明确声明 "bundles the WinDivert binaries from WinDivert-1.3.0-WDDK.zip"。
4. `pydivert/windivert.py` 的 `is_registered()`/`unregister()` 硬编码服务名 **`WinDivert1.3`**（`sc query WinDivert1.3`）。
5. 全仓库无任何脚本/代码在运行时注册或加载仓库 `windivert/` 下的 1.1.x 二进制：唯一的 `CreateService`/`OpenService` 代码（`winutil.py:489-671`）管理的是 `Dnscache` 服务，不是 WinDivert；无 `install.bat`/`install.ps1`/驱动注册脚本。WinDivert 由 pydivert 的 1.3.0 DLL 在首次 `WinDivertOpen`（`windows.py:591`）时自注册，注册的服务名是 `WinDivert1.3`。

**结论：部署到目标 VM 后，实际运行的 WinDivert 驱动是 1.3.0（服务名 `WinDivert1.3`），不是方案反复声称的 1.1.8。**

**为什么这是严重问题：**

1. 方案 §15.1 阻断条件之一"必须升级 WinDivert/驱动才能取得可靠身份"的判断基础是错的——当前根本不是 1.1.8。如果首 SYN owner 门禁失败，"是否升级驱动"的决策必须基于 1.3.0 的真实行为，而非一个从未运行的 1.1.8 幻影。
2. §21.0/§22.6.1 把"WinDivert 1.1.8 下首 SYN owner 是否稳定"列为严重未决风险——这个风险描述的版本号本身错了，等于风险登记表指向了一个不存在的运行时。
3. 1.3.0 与 1.1.8 在 NETWORK 层调用顺序、包地址语义、`WinDivertRecvEx`（1.3 新增，`pydivert/windivert_dll/__init__.py:71` 绑定但 pydivert 2.1.0 未暴露）等方面存在差异；Phase A 门禁必须在 1.3.0 上重做并据此结论。
4. 这也暴露一个配置卫生问题：仓库同时打包两套 WinDivert 二进制（1.1.x 死代码 + 1.3.0 实际运行），是潜在的混淆源。建议在 v2 中明确"运行时驱动版本 = pydivert 自带版本"，并考虑清理或文档化仓库 `windivert/` 的角色。

**建议修正：**

- 升版 v2，将所有"WinDivert 1.1.8"改为"WinDivert 1.3.0（由 `pydivert==2.1.0` 自带，服务名 `WinDivert1.3`）"。
- §15.1、§17、§18 中关于"升级驱动"的阻断条件改为以 1.3.0 为基线重新表述。
- Phase A 门禁（§22.5）的 VM 环境记录必须显式包含 `sc query WinDivert1.3` 与驱动文件版本，证明门禁跑在真实 1.3.0 上。
- 在 v2 中补一节"依赖版本来源核对"，固化"运行时驱动版本以 pydivert 包内二进制 + `sc query` 输出为准，不以仓库 `windivert/` 目录为准"。

### M2（中·设计错误）§8.3 的"插入"实际是现有裁决链的重排序

**方案主张（§8.3）：** 新进程重定向位于优先级 3，列出顺序为：
1. control permit → 2. relay return fixup → **3. 进程重定向** → 4. takeover sink → 5. relay forward / new SYN → 6. reviewed IPv4 → 7. FakeNet diversion/失败关闭。

**实际情况：** 现有裁决链（`windows.py:758-912`）的真实顺序为：
1. IPv6/空包守卫 → 2. reviewed-IPv4 分片守卫 → 3. control permit（`793-804`）→ 4. relay return fixup（`806-822`）→ **5. takeover sink（`824-838`）** → 6. relay forward / new SYN TLS relay（`840-855`）→ 7. reviewed IPv4（`856-873`）→ 8. divert（`875-881`）→ 9. 终判（`883-899`）。

即现有代码中 **takeover sink 在 relay forward/SYN 之前**。方案把进程重定向放在 takeover sink 之前（优先级 3 < 4），等于把"进程重定向"插在 relay return fixup 与 takeover sink **之间**——这确实如方案意图那样让进程重定向先于 takeover，但方案把它描述为"在现有全部出站捕获之外只增加一个分支"（§8.1）和"在规定位置调用"（§8.2），未明确指出**这同时把 takeover sink 的相对执行位置后移了一位**。

**为什么需要披露：**

- 如果 `A == takeover_ipv4`（公网 A 与私网 takeover sink 不同类，理论不可能，但配置层面若误配），或 `B` 与 takeover sink 的交互（§4.3 item 10 已禁止 `B == takeover_ipv4`）需要在裁决链中体现，相对顺序变化会影响测试预期。
- 更现实的风险：takeover 当前对**所有**发往 `takeover_ipv4` 的包（不限进程、不限端口 1-65535）生效。把进程重定向插在它之前，意味着目标进程发往 `A`（公网）的流量会先被进程重定向截走，**不会**落入 takeover——这是期望的。但非目标进程发往 `A` 的流量，按 §21.8.1 第 2 项"继续既有裁决"，会继续走到 takeover sink（位置 5）。方案没有显式说明"非目标进程对 A 的流量，takeover 不应介入（因为 A 是公网、takeover_ipv4 是私网，二者不同）"这一推理，也没有测试用例覆盖"A 与 takeover_ipv4 不重叠时，非目标进程对 A 的流量不被 takeover 误吃"。

**建议修正：**

- §8.3 明确标注：本变更**同时将 takeover sink 的执行位置从现有第 5 步后移至第 6 步之后**（相对进程重定向），并说明此重排序不影响 takeover 对 `takeover_ipv4` 的捕获（因 A 为公网、`takeover_ipv4` 为私网，二者地址类别不同，无交集）。
- §13.1 测试清单第 13 项（DeepSeek/takeover/reviewed IPv4 回归）显式增加："非目标进程对 A 的流量不被 takeover 误捕"用例。
- 若项目负责人认为 takeover 的相对位置不可移动，则需在 v2 中改为把进程重定向放在 takeover sink **之后**，并重新评估"目标进程对 A 流量是否会被 takeover 先吃"（不会，因地址不同，但需测试证明）。

### M3（中·表述错误）"明确非目标进程继续 domain relay 路径"在无 lease 场景不可达，表述过于乐观

**方案主张（§8.3 第 4 条、§21.8.1 第 2 项）：** owner `RESOLVED` 为明确非目标进程时，"继续既有 domain relay、reviewed IP、FakeNet diversion 或失败关闭裁决"。并将其归为"明确非目标进程兼容性透传，不是失败 fallback"。

**实际情况：** domain relay 的触发条件是 `lease_for(pkt.dst_ip, pkt.dport)`（`windows.py:1013` → `egresspolicy.py:787-799`），而 lease 仅由 DNS 解析允许域名时填充（`replaceDnsLeases`，`egresspolicy.py:763-785`，经 DNS listener 路径）。更关键：`lease_for` 强制要求 `int(port) in self.allowed_tcp_ports`，而 `allowed_tcp_ports` 被硬校验为**恰好 `{443}`**（`egresspolicy.py:428-429`）。

因此"明确非目标进程对 A 的流量继续走 domain relay"只在以下严格条件下可达：
- A 是经 DNS 解析某允许域名得到的 IP，且该 lease 仍有效；**且**
- 目标端口恰好是 443。

对于以下两种实际常见的非目标场景，domain relay 路径**根本不存在**：
1. **字面量 IP 连接到 A，A 未经任何允许域名 DNS 解析**：`lease_for(A, *)` 返回 `None`，relay 块（`842-854`）空转，包直接落到 reviewed IPv4（`856`）或 divert/drop。此时"兼容性透传"退化为"继续 reviewed IP / divert"，方案却把它表述为"继续 domain relay"。
2. **目标端口非 443**（例如目标进程硬编码 `A:8080`，非目标进程也连 `A:8080`）：即使 A 有 lease，`lease_for` 因端口不在 `{443}` 返回 `None`，同样不进 relay。

**为什么这是实质问题（而非咬文嚼字）：**

方案 §8.3 第 5 条与 §19 item 7 把"owner 未决时对 A 的包直接丢弃"作为失败关闭预期，并询问"是否符合预期"。这个丢弃的真实影响范围被 §8.3/§21.8.1 的乐观表述低估了：

- 当 A 与某允许域名 IP 重叠且端口 443 时，owner 未决丢弃确实会让正常分析工具的 DeepSeek TLS 连接失败——方案 §21.13 item 13 已意识到这一点。
- 但当 A 是**纯字面量 IP、无 lease**时，"明确非目标进程继续 domain relay"是**不可达**的；此时非目标进程对 A 的流量本就不会进 relay，方案的"兼容性透传"承诺对这一常见场景是空头支票。
- 更隐蔽的：owner 未决丢弃会把"原本会被 reviewed IPv4 放行的非目标进程对 A 的流量"也一起丢掉（因为丢弃发生在 reviewed IPv4 之前）。方案没有测试用例覆盖"A 同时是 reviewed IPv4 规则目标 + owner 未决"时的丢弃行为是否可接受。

**建议修正：**

- §8.3/§21.8.1 将"继续既有 domain relay、reviewed IP、FakeNet diversion 裁决"改为如实表述："继续既有裁决链（control permit 已过；relay 仅在 A 存在有效 443 lease 时触发；否则继续到 reviewed IPv4 / divert / 失败关闭）"。明确指出 domain relay 透传**仅在 A 有 443 lease 时可达**。
- §19 item 6/7 的询问补充："owner 未决时丢弃所有对 A 的包，**包括那些原本会被 reviewed IPv4 放行的非目标流量**，是否符合预期？"让项目负责人在知晓此范围后再决定。
- §13.1/§13.4 增加测试用例：(a) A 无 lease + 非目标进程 + 非 443 端口 → 不进 relay、不被进程重定向、按 reviewed IPv4/divert 处理；(b) A 有 443 lease + owner 未决 → 丢弃，并验证被丢弃的连接本应进 relay。

## 3. fallback 清单与合理性评估（按方案要求专项列出）

方案在 §11.2、§16、§21.12、§22.6.5 多处声明 fallback。审计逐一核实，方案**实际包含的 fallback/降级行为如下**：

### 3.1 明确声明"不存在"的 fallback（核实为真）

| 方案声明的"不存在"fallback | 核实 | 说明 |
|---|---|---|
| B 失败后直连真实公网 A | ✅ 方案确实未设计此 fallback | §11.2、§21.12 明确拒绝；裁决链中也无"A 重定向失败 → 放行 A"分支 |
| owner 失败后按端口/basename/PID-only/命令行猜测 | ✅ 确实未设计 | §5.1、§6.3、§21.3.4 明确拒绝；严格 resolver 要求完整元组 |
| route 失败后切换接口/启用 weak-host/源地址 NAT | ✅ 确实未设计 | §21.1.1、§21.1.3 明确拒绝；启动失败即拒启动 |
| 失败后进入 takeover/默认 listener/其他私网目标 | ✅ 确实未设计 | §6.3、§21.12 明确拒绝 |
| 自动升级 WinDivert/改 Firewall/启动宿主机服务 | ✅ 确实未设计 | §21.12 明确拒绝；§15.1 将"必须升级驱动"列为阻断条件 |
| B 不可达时选择其他目标 | ✅ 确实未设计 | §11.1、§17 明确失败关闭 |

**结论：方案声明的"无运行时目标切换 fallback"是真实可信的，没有发现隐藏的降级路径。**

### 3.2 明确声明的"兼容性透传"（方案明确分类为非 fallback）

| 兼容性透传 | 方案归类 | 审计意见 |
|---|---|---|
| ① owner `RESOLVED` 为明确非目标进程后继续现有裁决链 | §21.12 第 1 项，明确"不是 fallback" | **归类正确但表述需修正（见 M3）**：它确实不是目标切换 fallback，但"继续 domain relay"的可达性被高估 |
| ② 完全不属于映射/墓碑的 B 入站包原样重注入 | §21.12 第 2 项，明确"不是 fallback" | **归类正确且必要**：现有代码已有"直接访问 B 的其他合法连接"（如 takeover 也用 B），不加此透传会破坏它们；但 §21.9.3 已正确识别其与 WFP 驱动循环的风险并设为阻断门禁，合理 |

### 3.3 方案未明确归类、但实质是"边界行为"的项（建议显式澄清）

| 行为 | 现状 | 审计建议 |
|---|---|---|
| WinDivert handle 关闭后 Windows 恢复正常网络路径，存活目标进程可能重传到真实 A | §21.2、§21.12 末段已明确"这是平台生命周期事实，不是 v1 主动提供的 fallback" | **归类正确**，且 §22.1.2 用 READY 生命周期顺序与 runner 持有客户端 handle 来缩小该窗口，合理 |
| Phase A 门禁失败时"停止实施、记录证据、升版方案" | §11.2 末段、§22.5 明确"这是实施门禁，不是运行时 fallback" | **归类正确**，Phase A 是审核后实施的第一阻断门禁，不进入运行时 |
| owner 查询预算耗尽时"超预算新 SYN 直接丢弃" | §21.4.1、§22.2 表格 | 方案未显式把它归入 fallback 或失败关闭。它实质是**失败关闭**（不是降级到其他目标），建议 §21.4.1 显式标注"预算耗尽 = 失败关闭，非 fallback" |

**fallback 总评：方案的 fallback 声明是严谨的、分类基本正确；唯一问题是 M3 中"兼容性透传①"的可达性被高估，需在 v2 中如实修正表述。没有发现被隐瞒的降级路径。**

## 4. 实施步骤细化不足项（R1–R4）

### R1（中）§5.3 owner resolver 的"再次复核"时机未细化

方案 §5.3 第 7 项"路径、PID、创建时间在映射创建前再次复核"——但 §22.3 又要求 `prepare()` 内部不得在持有 NAT 锁时调用 owner resolver/哈希/route 查询，要"先在锁内建立有界查询 reservation，释放锁后调用 adapter，再重新加锁验证"。这两处的"复核"与"重新加锁验证"之间是否包含对进程身份（PID+创建时间+文件 ID）的**第二次** Windows API 查询，还是只比对 reservation 期间缓存的值，方案没有写清。

**建议：** v2 在 §22.3 明确：commit 前的"复核"是指重新加锁后比对该 SYN 在 reservation 期间缓存的 `(PID, creation_time, file_id)` 与当前 Windows 进程快照是否仍一致；若不一致（如进程已退出或创建时间变化）则 abort，不重新查询 owner row。

### R2（中）§21.9.1 入站 filter 的 1.1.8/1.3.0 语法兼容性未验证

方案 §22.1.4 提到"filter 的具体 1.1.8 语法必须通过 `WinDivertHelperCheckFilter/EvalFilter` 和 VM 抓包验证"，但：

1. 实际运行的是 1.3.0（M1），不是 1.1.8；
2. §21.9.1 给出的 filter `inbound and ip and tcp and src == B and dst == FrozenLocalIPv4` 需验证 1.3.0 的 filter parser 接受；
3. §22.1.4 还要求"入站 filter 必须覆盖 TCP 或 IPv4 分片，不能因非首片没有 TCP header 而绕过"——1.3.0 的 `ip and tcp` 对纯 IP 分片（非首片，无 TCP header）的匹配行为需要显式证明。WinDivert filter 中 `tcp` 关键字对非首片分片的求值在 1.3.0 文档中需核实（通常 `tcp` 对非首片返回 false，可能导致非首片分片绕过 `src==B` 分支——这与 §22.1.4 的"入站分片必须丢弃"冲突，需要用 `ip and (tcp or ip.Src == B ...)` 或类似写法覆盖）。

**建议：** v2 在 §22.1.4/§21.9.1 补充：(a) filter 验证基于 1.3.0；(b) 明确给出覆盖 IPv4 分片（含非首片）的 filter 写法，并要求 Phase A 用 `WinDivertHelperCheckFilter` + 实际分片抓包证明非首片不会绕过入站丢弃。

### R3（低）§22.2 容量初值的"每 PID 256 活动映射"与 §7.6 不一致

§7.6（v0）写"单 PID 256"，§22.2 表格也写"单 PID 活动映射 256"，一致。但 §22.2 表格的"活动映射总量 1024"意味着**至多 4 个 PID 各占满 256**就触达总量上限，第 5 个 PID 的第一个流即被总量丢弃。方案没有说明这个交互——对一个"单规则、单目标进程"的 v0 来说够用，但若目标进程是共享运行时（如 `python.exe`，§21.3.4 已警告），其所有连接都可能计入同一 PID 的 256 配额，可能很快耗尽。

**建议：** v2 在 §22.2 补注："单规则假设下 1024/256 配额充足；若目标进程为共享运行时宿主，其全部出站连接（不限目标 A）会被 PID 配额计数，需在 Phase A 实测目标进程的并发连接数是否逼近 256。"——核实：实际上方案 §21.4.1 规定 owner 查询只对 `dst=A` 的新 SYN 触发，活动映射也只对命中 A 的流创建，所以 PID 配额只计"该 PID 对 A 的并发流"，不是该 PID 的全部连接。方案应明确这一点（当前 §22.2 表格"单 PID 活动映射 256"未注明"仅计命中 A 的流"）。

### R4（低）§13.3 B sentinel 的"外部预置"与 §21.11.3 的"只读探测"边界

§13.3 角色描述 B sentinel"由测试环境外部预置"，§21.11.3 又说"一键验收开始前必须只读探测审核端口并记录 nonce 协议版本。探测失败直接退出，不改 DNS、不打开 WinDivert"。这两处对 sentinel 的生命周期责任清晰，但**没说明探测用的源地址/接口**——如果探测包从 FrozenLocalIPv4 之外的地址发出，或经过非 FrozenInterfaceIndex 的接口，探测结果不能代表后续重定向流的真实可达性。

**建议：** v2 在 §21.11.3 补充："B sentinel 探测必须从 FrozenLocalIPv4 经 FrozenInterfaceIndex 发起，与重定向流的源/接口一致；否则探测通过不能代表运行期可达。"

## 5. 遗漏与需补充披露项（O1–O5）

### O1（中）仓库 `windivert/` 1.1.x 死代码的混淆风险未披露

见 M1。仓库同时存在两套 WinDivert 二进制，且 `fakenet.spec` 把死的 1.1.x 也打包进交付包。方案完全没提到这一配置卫生问题。建议 v2 补一节"依赖版本来源核对"，并建议项目负责人决定是否清理仓库 `windivert/` 或在 README 明确其不被加载。

### O2（中）`get_pid_comm` 在 legacy 路径仍是每包调用，与方案"owner 查询只在新 SYN"的对比未利用

方案 §3.3 批评现有 `get_pid_comm` 不足授权，§21.4.1 强调 owner 查询只在新 SYN。但审计发现：现有 `get_pid_comm` 在 legacy `handle_pkt` 路径（`diverterbase.py:1431`）仍是**每包调用** `GetExtendedTcpTable`（固定 512 行、无缓存、无重试）。

这意味着：(a) 严格 resolver 的"完整元组查询 + 动态 buffer + 哈希复核"如果实现得当，单次成本未必高于现有 legacy 每包成本；(b) 但方案没有利用这一对照来论证 owner 查询预算（32/秒）的合理性，反而把单 receiver 线程饥饿作为新风险——实际上现有 legacy 路径早已在每包付这个成本。

**建议：** v2 在 §21.4 性能论证中补充对照："现有 legacy 路径已对每个 diverted 包调用 `GetExtendedTcpTable`（512 行固定缓冲、无缓存）；严格 resolver 改为仅对新 A SYN 查询、带动态 buffer 与身份缓存，单流成本相当或更低，但 SYN 突发下的预算控制是新约束。" 这能让审核者更准确评估性能风险。

### O3（中）`ExternalTakeoverProbeTCPPorts` 在运行时不约束 sink 的事实未披露

§4.3 item 10 与 §21.7 讨论 B 的全端口暴露。审计发现现有 takeover 已是全端口 sink（`matches_takeover_sink` 仅要求 `1 <= dport <= 65535`，`egresspolicy.py:701`），而 `ExternalTakeoverProbeTCPPorts` 只在 launcher（`Start-ReviewedIPv4.ps1:359`）做预探测，**运行时根本不读它、不约束 sink**。

§21.7 把全端口暴露描述为新风险，但实际现有 takeover 已有相同性质。方案应明确："全端口暴露风险**与现有 takeover 一致**，不是本方案新引入的；现有 `ExternalTakeoverProbeTCPPorts` 不在运行时约束 sink，本项目此前已接受 takeover 的全端口暴露。" 这能让项目负责人基于一致的标准决定是否接受进程重定向的全端口暴露。

### O4（低）现有 reviewed-IPv4 分片守卫已存在，方案的"分片失败关闭"是复用而非全新

§22.1.4 提出分片必须失败关闭。审计发现现有 `classify_reviewed_ipv4_fragment`（`windows.py:925-940`）已存在并对 reviewed-IPv4 分片失败关闭（`windows.py:777-784`，`DROP_EXTERNAL`）。方案应明确指出："分片失败关闭**复用现有 `classify_reviewed_ipv4_fragment` 机制**，扩展到对 A/B 的分片；不是全新路径。" 这能降低审核者对"新分片逻辑"的担忧，因为现有机制已经过验收。

### O5（低）§4.3 item 9（A 不得出现在 reviewed IPv4 规则）的检查已部分存在

§4.3 item 9 要求 A 不得与静态 `ExternalAllowedIPv4Rules` 冲突。审计发现 `egresspolicy.py:311-315` 已实现"reviewed IPv4 不得等于 takeover_ipv4"的冲突检查。v2 应明确：item 9 的检查可复用同一 `_parse_reviewed_ipv4_rules` 返回的 `frozenset`（`egresspolicy.py:374`）做 `A in reviewed_set` 判断，实现成本极低；item 10（B 不得与 takeover 相同）甚至可由现有 `311-315` 的对称检查覆盖。

## 6. 风险与副作用披露的完整性评估

方案 §17（v0）与 §21（v1）的风险清单总体充分。审计核实：

**披露充分且控制措施得当的风险：**
- 首 SYN owner 稳定性（严重，Phase A 门禁）——✅ 但版本号错（M1）
- PID 重用/端口复用（高，创建时间+generation+墓碑）——✅
- 入站 filter 破坏其他 B 连接（高，只捕 `src==B`+无映射原样重注入）——✅
- 与 DeepSeek/domain relay 优先级冲突（高）——✅ 但需结合 M3 修正可达性表述
- B route 漂移（高，启动冻结+运行复核）——✅
- 状态表/日志耗尽（高，总量/单 PID 限额+限速）——✅ 但需补 R3 的配额交互说明
- WinDivert 重注入循环（高，地址变化后 filter 不再命中+循环测试为阻断门禁）——✅ 且 §22.1.5 补充了出站重注入循环
- 进程经 broker/proxy 发流（中至高，按实际 socket owner）——✅
- WFP 共存循环（§21.9.3 共存阻断门禁）——✅

**被低估或未充分披露的：**
- **M1 的版本错误**导致"必须升级驱动"这一阻断条件的基线错位——严重低估，必须修正。
- **M3 的可达性高估**导致"owner 未决丢弃"对正常工具（尤其 A 与 reviewed IPv4 重叠、或 A 无 lease 字面量连接）的影响范围被低估。
- **O3 的全端口暴露**被表述为新风险，实际与现有 takeover 一致——不是低估风险本身，而是低估了"项目此前已接受同类风险"这一既有共识，可能让审核者误以为是全新风险敞口。

**未被破坏的现有机制核实：**
- DeepSeek 域名放行、域名 TLS relay、私网 takeover、reviewed IPv4、FakeNet 本地 diversion、双 PCAP、停止恢复——方案 §2.1 item 7 声明保持，审计核实裁决链插入位置（经 M2 修正后）不破坏这些机制的功能；唯一行为变化是 takeover sink 的相对执行位置后移一位（M2），以及 owner 未决时对 A 的流量被新增丢弃（M3）。

## 7. 审核结论与升版建议

### 7.1 审核结论：有条件不通过

方案设计纪律、风险意识与 fallback 声明整体优秀，但存在必须修正的实质问题，不能在当前 v1 版本下批准实施：

1. **M1（严重·事实错误）**：WinDivert 运行时版本为 1.3.0 而非 1.1.8，动摇可行性论证与阻断条件基线。
2. **M2（中·设计错误）**：§8.3 的"插入"实为现有裁决链重排序（takeover sink 后移），未如实标注。
3. **M3（中·表述错误）**："明确非目标进程继续 domain relay 路径"在无 443 lease 场景不可达，表述过于乐观，低估了 owner 未决丢弃的影响范围。

### 7.2 升版要求

建议升版 **v2**，至少完成：

- [ ] M1：全文 WinDivert 版本改为 1.3.0（pydivert 自带，服务名 `WinDivert1.3`）；§15.1/§17/§18 阻断条件与风险以 1.3.0 为基线重述；Phase A 门禁 VM 环境记录显式包含 `sc query WinDivert1.3` 与驱动版本；新增"依赖版本来源核对"节（含 O1）。
- [ ] M2：§8.3 显式标注 takeover sink 相对位置后移；§13 增加"非目标进程对 A 流量不被 takeover 误捕"用例。
- [ ] M3：§8.3/§21.8.1 如实表述 domain relay 透传仅在 A 有 443 lease 时可达；§19 item 6/7 补充"owner 未决丢弃会波及本应被 reviewed IPv4 放行的非目标流量"；§13 增加无 lease / 非 443 端口的透传不可达用例。
- [ ] R1：§22.3 明确 commit 前"复核"的语义（比对缓存身份，非二次查询）。
- [ ] R2：§22.1.4/§21.9.1 基于 1.3.0 给出覆盖 IPv4 非首片分片的 filter 写法并要求 Phase A 验证。
- [ ] R3：§22.2 表格注明"单 PID 配额仅计命中 A 的流"。
- [ ] R4：§21.11.3 补充 sentinel 探测的源地址/接口约束。
- [ ] O2：§21.4 补充与现有 legacy 每包 `get_pid_comm` 成本的对照。
- [ ] O3：§21.7 明确全端口暴露与现有 takeover 一致。
- [ ] O4/O5：§22.1.4/§4.3 注明复用现有分片守卫与现有 reviewed 冲突检查。

### 7.3 不变项（v1 中已正确、v2 应保留）

- Windows-only、TCP-only、单规则、A 公网全局单播、B RFC1918、全 TCP 端口保持、无端口转换；
- A/B 同源同接口、拒绝源地址 NAT、拒绝 weak-host 依赖；
- owner 结果四态枚举 `RESOLVED/NOT_FOUND/AMBIGUOUS/ERROR`；
- `prepare/commit/abort` 事务 interface 与 exactly-once token；
- 无运行时目标切换 fallback（§3.1 核实为真）；
- 两个兼容性透传的明确分类（仅 M3 修正其①的可达性表述）；
- Phase A 实施门禁、§22.2 安全初值、独立挂起状态（不调全局 `suspend()`）；
- 审核通过前禁止实施。

### 7.4 审计保留意见

本审计**只审核、未执行**，未修改任何生产代码、配置、测试或交付包，未在宿主机运行 FakeNet-NG。审计基于 `ef417ab` 代码基线与方案 v1 文本；若 v2 修正上述项，需重新审核。M1 的版本事实错误是本次审计的最重要发现，建议项目负责人优先确认 pydivert 自带 WinDivert 版本与运行时驱动注册行为。

## 8. 项目方复核答复（2026-08-06，追加）

本答复对审计意见进行了逐项代码交叉核对。认可内容已写入原方案 v2；下列为不同意、部分不同意或需要限定的内容及理由。本文只追加审计答复，不改写第三方原始审计正文。

### 8.1 对 M1 绝对化结论的限定驳斥

**不同意内容：** “仓库 `windivert/` 的 1.1.x 二进制在运行时从不被加载”“部署到目标 VM 后实际运行的一定是 1.3.0”。

**驳斥原因：** 审计证明了源码/wheel 运行方式下 `pydivert==2.1.0` 的包内 DLL 路径和 `WinDivert1.3` 服务名，这一核心事实成立；但 `fakenet.spec` 又把仓库 `windivert/` 的另一套 DLL/SYS 加入冻结产物。审计没有对实际交付的 frozen 产物执行模块加载路径、DLL/SYS hash 和服务注册取证，因此不能从源码导入逻辑外推为“所有交付形态从不加载”。原方案 v2 已把预期基线改为 1.3.0，同时要求 Phase A 在实际交付形态中证明加载路径、版本、hash 和服务；证据不一致即阻断。这比直接把未经运行证明的绝对结论写成事实更稳妥。

### 8.2 对 M2“既有裁决链重排序”的驳斥

**不同意内容：** 新增 process redirect 使 takeover sink “相对执行位置后移”，构成既有裁决链重排序或设计错误。

**驳斥原因：** 新功能是在 `relay return fixup` 与 `takeover sink` 之间增加一个互斥分支。control、relay return、takeover、domain relay、reviewed IPv4、diversion 等任意两个既有机制之间的相对顺序均未改变。takeover 的显示序号从旧链中的第 N 项变成新链中的第 N+1 项，只是插入后的序号变化，不是既有机制重排。合法配置中 `A` 为公网全局单播，takeover 为 RFC1918，且 `B == takeover_ipv4` 被拒绝，地址域互斥。v2 接受审计建议增加回归用例，但不接受“设计错误”定性，也不会写入不存在的既有机制重排序。

### 8.3 对 M3 部分推论的驳斥

**不同意内容一：** 把“继续既有 domain relay、reviewed IP、divert 等裁决”解释成保证进入 domain relay，并称无 lease 场景的兼容性透传是“空头支票”。

**驳斥原因：** v1 使用“继续既有裁决链”的枚举表述，本义是继续尝试各既有分支，不是保证某一分支命中。审计指出 relay 只在有效 DNS lease 且端口 443 时可达，这一精确条件有助于消除歧义，已纳入 v2；但无 lease 时继续到 diversion/drop 仍然是“继续既有裁决”，不能据此称整个兼容性透传承诺为空。

**不同意内容二：** 要求验收 `A` 同时位于 `ExternalAllowedIPv4Rules` 且 owner 未决的运行期场景。

**驳斥原因：** 原方案 §4.3 item 9 已要求启用本功能时 `A` 不得出现在静态 reviewed IPv4 规则中，冲突必须在打开 WinDivert 前拒绝。让运行期验收构造一个启动合同明确禁止的配置会自相矛盾。v2 改为测试该冲突能否启动前拒绝；owner 未决对有效 443 lease 流量的失败关闭则单独测试。

### 8.4 对 R1 复核方式与时机的限定驳斥

**不同意内容：** 将复核定义为只比较 reservation 缓存身份且“不重新查询”，或把 Windows 进程快照复核放在发送后的 `commit()` 前后语义中。

**驳斥原因：** 只把缓存值与同一缓存再比较无法发现进程退出或 PID 重用，不构成 TOCTOU 防护。v2 规定只做一次 `GetExtendedTcpTable` owner-row 全表枚举，但在返回可发送 decision/token 前，用有界进程 handle 查询轻量复核 PID 创建时间、最终映像路径和文件身份；失败则撤销 reservation。发送后的 `commit()` 只处理内存状态，届时才发现身份变化已经无法撤回已注入的数据包。因此接受“需要再次复核”的目标，不接受“完全不做第二次 Windows 进程查询”或把复核推迟到发送后的实现。

### 8.5 对 O1 清理建议的范围限定

**不同意内容：** 把清理仓库 `windivert/` 作为本功能 v2 的附带修正。

**驳斥原因：** 两套二进制确实需要披露和取证，已纳入 v2；但当前尚未证明冻结构建对仓库二进制完全无依赖，直接清理可能破坏既有 PyInstaller 交付。清理依赖属于独立打包变更，需要单独影响分析与审核，不能在本功能实施中顺带执行。

### 8.6 对 O2 性能推论的驳斥

**不同意内容：** 因 legacy `handle_pkt` 已按包调用 `get_pid_comm`，严格 resolver 的单流成本可视为“相当或更低”，单 receiver 饥饿不算新的风险面。

**驳斥原因：** legacy 每包 owner 查询是事实，已纳入 v2 的性能对照；但 `DomainAllowList` 的 control、takeover、relay、reviewed 等路径可以在进入 legacy `handle_pkt` 前结束。process redirect 插入后，对 `A` 的新 SYN 会执行更严格的动态 owner buffer、进程 handle 和身份复核，这对原本早期短路的流量是新增成本。没有 VM 基准数据前不能断言成本相当或更低，查询预算、SYN 洪泛和单 receiver 饥饿仍是阻断门禁。

### 8.7 对 O3 风险继承结论的驳斥

**不同意内容：** process redirect 的全端口风险“不是本方案新引入”，项目此前接受 takeover 的全端口性质即可视为接受本功能风险。

**驳斥原因：** 现有 takeover 确实按全端口捕获，`ExternalTakeoverProbeTCPPorts` 也确实只用于探测，这两个事实已纳入 v2。但新功能新增了“审核进程访问公网 `A:any` 被导向私网 `B:any`”的授权路径，且方案明确禁止 `B` 等于 takeover 地址；目标主体、触发条件和可能暴露的私网主机均可不同。既有风险接受不能自动转移。本功能仍需单独明确接受全端口风险，probe 端口也不得被误作运行时限制。

### 8.8 对 O4“现有分片路径可直接复用”的限定驳斥

**不同意内容：** A/B 分片失败关闭只是复用现有 `classify_reviewed_ipv4_fragment`，因而不是新的实现路径或可降低关注度。

**驳斥原因：** 现有 helper 从原始 IPv4 header 读取 fragment bits 的模式可以复用，但它只用目的地址和 reviewed `target_protocols` 判断出站流量，不能直接识别 `src=B,dst=L` 的入站非首片。启用入站捕获本身也是新路径。v2 要求方向感知泛化，并用 `ip.Protocol == 6` 的 filter 和 Phase A 非首片语料验证；不能因为存在一个相似 helper 就降低该门禁。

### 8.9 对 O5“现有冲突检查对称覆盖”的驳斥

**不同意内容：** `B == takeover_ipv4` 可由 `_parse_reviewed_ipv4_rules` 现有检查对称覆盖，item 10 基本无需新增检查。

**驳斥原因：** 现有代码检查的是“每个 reviewed IPv4 地址是否等于 takeover/DNS/local 地址”，输入中没有 process redirect 的 `B`，也没有检查 `B` 与 takeover 的关系。实现可以复用 reviewed 集合检查 `A in reviewed_set`，但 `B == takeover_ipv4` 必须由新的跨功能冲突校验显式拒绝。二者不是对称的已有检查。

### 8.10 复核结论

除上述驳斥和限定外，审计关于 WinDivert 1.3.0 核心基线、domain relay 的有效 443 lease 条件、预算耗尽失败关闭、IPv4 非首片捕获、配额口径、sentinel 绑定冻结源/接口、双二进制披露及 probe 不约束运行时端口等意见均已引入原方案 v2。

原方案 v2 当前仍是“待第三方复审，禁止实施”。本答复不代表审计自动通过，也不授权实施。
