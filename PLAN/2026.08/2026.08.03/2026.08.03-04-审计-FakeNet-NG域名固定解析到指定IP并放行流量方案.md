- 审计对象: `2026.08.03-03-FakeNet-NG域名固定解析到指定IP并放行流量方案.md`
- 审计对象版本: **v4**(2026-08-04); v1/v2 已作废, 本审计针对 v4

## 0. 审计概要

v4 相对 v2 是**方向反转**(§1.1): `api.deepseek.com` 不再固定公网 IP, 而是保持已验收的动态 `DomainAllowList` 链; 其他域名的 A 查询统一合成私网接管地址 `192.168.204.1`, 并由新裁决 `ALLOW_TAKEOVER_SINK` 在 legacy 本地重定向前按原始 TCP/UDP 端口直送。因此**上一版(2026.08.03-04 初版)对 v1/v2 的审计意见不能移植到 v4**, 本文档已整体重写。

审计做了三类核实:

1. **代码事实**: v4 涉及的 DNSListener 分支点、Windows 裁决顺序、EgressPolicy 约束与现网代码逐条核对, 全部吻合(见 §1 表)。
2. **外部依赖事实**: `netifaces_plus-0.12.5-cp313-cp313-win_amd64.whl` 与 `pydivert-2.1.0-py2.py3-none-any.whl` 的 SHA-256 与 PyPI JSON API 实测值**完全一致**; netifaces-plus 的 cp313 win_amd64 wheel 内部确实提供 `netifaces/__init__.py` 导入模块与 `_netifaces.cp313-win_amd64.pyd`; pydivert 2.1.0 wheel 确实内含 `pydivert/windivert.py` 与捆绑的 WinDivert32/64.dll/.sys。
3. **环境证据**: 仓库内 `2026.08.03-01-...方案.md`(第 785/826/899/1019 行)记录了 Windows 10 `10.0.19045` + Python 3.13 的 VM 验收日志、测试前解析器 `192.168.204.2`(与接管地址同属 host-only `192.168.204.0/24` 网段), 且代码库已包含 Python 3.13 专门修复(ProxyListener SSLSocket 回归, `test_proxy_listener.py`)——"已有 VM 证据基线"主张在仓库内有依据。

**关键简化**: v4 仍要求 `ExternalDnsServer`(DeepSeek 用), 因此**不需要修改 `DiverterBase` 的公共 DNS 前置条件, 也不需要改 `EgressPolicy` 构造签名**。v2 审计中最高的"公共门禁放松导致动态模式无 DNS 误启动"风险在 v4 中整体消失。这是 v4 相对 v2 最大的风险降低点, 方案 §1.2/§9 与此一致。

## 2. 发现与不同意见

### N1(中): 接管模式的激活判据未写成显式合同

- §4.1 说"新增独立配置文件"并规定其字段, §4.5 规定接管配置的失败条件, 但**"何时进入接管模式"没有一条显式规则**: 建议成文为——`ExternalTakeoverIPv4` 缺失时保持现有动态 `DomainAllowList` 语义; 该 key 出现(含空值)即接管模式, 此后 §4.5 所列接管字段全部必填, 缺失/为空即启动失败。
- 若不写清, 实现者可能把"专用 INI 缺 key"当普通模式静默运行(绕过接管合同), 或把"动态 INI 被误加空 key"当接管模式误启动。两条都偏离合同。
- 建议: §4.1 或 §4.5 增加一条"模式激活判据", 并补一个纯配置测试(缺 key → 普通模式; 空 key → 接管模式且启动失败)。

### N2(中): sink 直送的路由/出站接口验收未写入合同

- sink 裁决只按目标 IP 放行并重注入; 若 VM 多网卡且对 `192.168.204.0/24` 无直连路由, 重注入后的包可能经默认网关接口出站, 使"发往接管地址"的流量实际上从另一个网络接口离开 VM。当前验收环境(host-only 同网段直连)不存在该问题, 但合同层面未防未来环境漂移。
- 建议: §11.4/§12 增加——启动前/验收时记录 `Get-NetRoute`/`route print` 中 `192.168.204.0/24` 的接口归属; 独立 PCAP 确认 sink 出站包走 host-only 接口; 启动器**不做任何路由修改**; 多网卡 VM 作为验收环境之一。

### N3(低): 接管 A 响应与 Windows Dnscache 周期性刷新

- TTL=60 下, Dnscache 约每 30s 对已缓存域名发起刷新查询, 每个被缓存的非允许域名都会周期性触发 `TAKEOVER_DNS_ANSWER`。这不是 fallback 也不是续期问题(接管响应无 lease), 但会产生周期性日志, 且"TTL 过期行为"的验收需在查询静止期进行。
- §13 已要求限速; 建议 §10/§11 注明"Dnscache 刷新导致的周期性接管响应为预期事件, 不作为异常判据", 与既有动态链的 `DNS_LEASE_ADD` 刷新语义保持一致。

### N4(低): 接管权威响应的 AA 标志未规定

- §5.2-5 写"权威 A 响应", 但未固定 AA 位(动态链为 aa=0, `DNSListener.py:404-406`)。建议固定接管响应 `aa=1`(宣称权威, 与"合成权威应答"语义一致)并在测试断言中写明, 避免实现随意取值。

### N5(低): 可选 TCP 探测的 API 与超时语义未固定

- §4.4 规定了"TCP connect、无应用数据、每端口一次、超时 500ms", 但未指定实现 API。PowerShell 的 `Test-NetConnection` 会附带 ping/路由痕迹, `TcpClient.Connect()` 无精确超时控制, `TcpClient.ConnectAsync()` 才可精确实现 500ms 语义。
- 建议: §4.4 固定实现方式(如 `Socket.ConnectAsync` + 精确 timeout, 或 `TcpClient` + 自定义超时), 使"超时 500ms、每端口一次、不发送数据"可测试、可复现。

### N6(低): sink 返回流量不受策略约束, 应显式声明为残余边界

- WinDivert filter 只捕获 outbound(`windows.py:142-143`), sink 的返回流量(宿主 → VM, 入站)完全不被 FakeNet 检查。这是与现有 DNS upstream/relay 相同的固有边界, 但 v4 新增了"样本 → 宿主"的数据面, 审计建议在 §16 审核重点中显式声明:**FakeNet 无法阻止宿主(或冒充宿主的对端)向 VM 注入返回流量; 该边界与"宿主监听器非目标"一致, 由项目负责人已接受的宿主安全假设覆盖。**

### N7(低): §11.5 负向矩阵措辞精确化

- §11.5"非允许公网域名、DoH、DoT、UDP443 和外部 IPv6 保持现有失败关闭/本地分析边界"——在接管模式下, **经 DNS 的非允许域名一律先返回接管地址, 其流量不再进入 FakeNet 本地分析路径**;"本地分析边界"只适用于: 非 A 类型查询、硬编码 IP、DoH 等绕过 DNS 的流量, 以及接管 IP 以外的目标。
- 建议: §3 表/§11.5 改写为"非允许域名经 DNS 的 A 类流量 → sink; 绕过 DNS(硬编码 IP/DoH/DoT)、外部公网目标、UDP443(外部)和 IPv6 → 现有失败关闭/本地分析边界"。UDP/443 到接管地址会被 sink 直送(§4.3 全端口), 该点也应在负向矩阵中写明"仅外部 UDP/443 失败关闭"。

### N8(低): 探测端口与数据面解耦的断言已覆盖, 补充建议

- §11.2-12 已要求"探测列表不参与 sink verdict", §19.4 已识别解耦风险。补充一点: 建议纯策略测试断言"即使探测端口等于接管 IP 的某个端口, sink 裁决结果不变", 并断言探测函数与策略层无共享可变状态。属测试补充, 不改变设计。

## 3. Fallback 复核(v4 添加的 fallback 及合理性)

v4 明确不增加运行时网络 fallback, 并经核对包含以下非运行时项:

| v4 中的 fallback/确定性选择 | 性质 | 条件/约束 | 合理性 |
|---|---|---|---|
| 可选 TCP 探测失败(CLOSED/TIMEOUT/ERROR)后继续启动(§4.4/§14) | 提示性观测, 非健康门禁 | 项目负责人明确授权; 结果仅四态日志; 不改变目标、端口、DNS、裁决或出口 | 合理。已显式排除"健康门禁/fallback"误读; UDP 不探测的理由(connect 不验证监听、发送数据破坏只探测边界)成立 |
| 探测配置为空时 skip(§4.4/§14) | 确定性配置默认 | 默认不探测; 记录 `TAKEOVER_PROBE_SKIP` | 合理 |
| 固定 `pydivert==2.1.0` 与 `netifaces-plus==0.12.5`(§8.3) | 确定性构建选择 | wheel 哈希已外部核实与 PyPI 一致; 拒绝自动升级到 pydivert 3.1.3(Windows 11 要求); 只写入专用 lock, 不改全局 setup.py | 合理。netifaces-plus 提供同名 `netifaces` 模块已实证; 接口面小且启动器做最小接口前置检查 |
| DeepSeek 受控 DNS/TLS 失败不回退接管地址、公共 DNS、DoH、hosts(§14) | 失败关闭 | 返回 SERVFAIL/连接失败 | 合理 |
| sink 不可达不回退真实 DNS、其他 IP、FakeNet 本机 listener(§14) | 失败关闭 | 连接失败/超时 | 合理 |
| takeover 子状态挂起只挂起接管、不破坏 DeepSeek(§6.3/§14) | 双失败域失败关闭 | 本机地址快照/全局异常才全局挂起 | 合理; 明确不是热恢复或备用路径 |
| 包内 wheelhouse 离线自举、DNS/VM 快照恢复(§14) | 确定性准备/运维回滚 | 不产生额外网络放行 | 合理 |

结论: 未发现 v4 添加不合理 fallback, 也未发现漏报的隐式运行时回退。N3(Dnscache 周期性刷新)是 Windows 系统行为, 不是方案添加的 fallback, 需在验收预期中说明。

## 4. 对现有机制的破坏评估

- **v2 高风险点已消除**: v4 不修改 `DiverterBase` DNS 前置条件(diverterbase.py:706-720)、不改 `EgressPolicy` 构造签名(`external_dns_server` 仍必填)、不动 Windows 非 DomainAllowList 路径。
- **共享路径改动仅两处, 且均为分支性**: (1) `DNSHandler.parse` 在 `allowed_root` 判断后插入接管 A 合成分支(动态路径和 Disabled/普通模式不变); (2) `windows.py` 裁决链在 relay 映射修复之后、legacy redirect 之前插入 sink 判定(permit 与 relay 修复优先于 sink, 与 §3 分类优先级一致)。
- **地址空间天然不相交, 裁决顺序无歧义**: permit 流(本地 → resolver/公网)、relay 映射流(本地 ↔ relay)、DeepSeek lease 流(公网)、sink 流(本地 → 192.168.204.1)目标互不重叠, 顺序冲突仅在实现层面存在理论可能, 由 §3 优先级 + 负向 PCAP 覆盖。
- **回归面收敛**: 现有 51 项分文件回归清单(§11.6)与实际测试计数一致; Python 3.13 兼容问题(ProxyListener SSLSocket)已有先例修复与测试, 依赖组合有仓库内 VM 证据。
- 未发现方案未识别且会破坏现有动态/Disabled 模式的机制性缺陷。

需补精确化的点: N1(激活判据)、N2(路由验收)、N4(AA 标志)、N5(探测 API)。以上均可文档层面修订, 不改变架构与代码基线。

## 7. 审计结论

- **正确性**: v4 对现状的描述与基线代码事实全部吻合; 两个关键依赖的 SHA-256 与 PyPI 实测一致, netifaces-plus 的 `netifaces` 导入模块已实证; "已有 VM 证据基线"在仓库内有据可查。未发现阻断性错误。
- **完整性**: N1/N2 两项中等级建议(激活判据成文、路由/出站接口验收)与若干低等级精确化建议, 均属合同补强; 风险表(§13)覆盖完整, 未发现被低估到影响决策的风险。
- **fallback**: 仅含非运行时确定性选择与失败关闭, 无隐式运行时回退; 探测失败继续启动的提示性语义已由项目负责人确认, 合理。
- **实施步骤**: 细化程度总体足够, 需按 N1/N2/N4/N5 补充 4 处精确化。

## 8. 方案方对 v4 审计的复核与处置（2026-08-04）

### 8.1 复核原则与结论

逐项结论:

### 8.2 同意并引入的具体内容

1. **N1**: v5规定 `ExternalTakeoverIPv4`完全缺失才保持动态模式; key出现即请求 takeover, 空值/非法值失败; 只有 TTL/probe等附属字段而无主字段也失败. 理由: 消除配置拼写或模板漂移导致的静默降级.
2. **N2中的合理部分**: v5新增只读路由前置门禁, 要求精确 `.1`具有唯一、非默认、on-link有效路由, 记录接口/源地址/前缀/next hop/metric, 并用多网卡 PCAP验收. 理由: sink packet重注入后仍由 Windows路由决定实际接口.
3. **N4**: v5固定接管 A响应 `qr=1, aa=1, ra=1, rcode=NOERROR`并回显 `rd`、transaction和question. 理由: 权威合成语义必须可断言, 且与现有普通合成响应一致.
4. **N5中的合理部分**: v5固定 PowerShell 5.1实现为数值 `IPAddress` + 每端口新 `TcpClient` + `ConnectAsync` task等待, 定义 OPEN/CLOSED/TIMEOUT/ERROR、finally释放、禁止 DNS/ICMP/Test-NetConnection/GetStream/send/write. 理由: 可复现且守住“只握手、不发送应用数据”边界.
5. **N6中的合理部分**: v5显式记录 WinDivert outbound-only导致返回流量不经过新增 sink verdict. 理由: 这是不能由 outbound数据面证明已缓解的残余边界.
6. **N7**: v5负向矩阵改为“经系统 DNS的非允许 A→sink; 硬编码 IP/DoH/DoT/其他外部目标/外部 UDP443/IPv6→现有边界”, 并明确 sink UDP443仍直送. 理由: 避免将两条路径混写.
7. **N8**: v5增加两份只改变 probe字段的配置必须产生同一策略/裁决、probe函数无共享可变状态且不是数据面决策输入的测试. 理由: 直接证明提示性探测不会改变放行范围.
8. **fallback复核**: 同意审计“未新增运行时网络 fallback”的结论. probe失败继续启动是项目负责人已明确批准的提示语义; 新增 route检查只会失败关闭, 不会切换地址、接口、DNS或策略.

### 8.3 不同意内容及驳斥理由

#### 驳斥一: “未发现阻断性缺陷”

不同意. 被审计的 v4原方案在 §7后含有字面量截断标记, §7合同正文丢失, 且 §8.4/§8.5在正式 §8之前重复一次. 这不是格式小问题: 审核者无法确定丢失的原始合同, 因而 v4文本本身不具备可实施性. 审计没有发现这一点却给出“未发现阻断性缺陷”, 其总体结论不能直接采信. v5已恢复 §7、删除重复章节, 并增加完整性检查门禁.

#### 驳斥二: “resolver为 `.2`且同网段, 所以 `.1`直连路由存在、无需新增路由”

只同意“不应自动新增路由”, 不同意其事实证明. VM能访问或配置 `192.168.204.2`只证明某时刻对 resolver存在可用路径, 不能证明精确 `.1`当前使用哪个接口、next hop是否 on-link、是否被更具体路由覆盖, 也不能证明未来多网卡快照无歧义. 因此 v5改为启动前实时验证唯一 on-link有效路由并禁止修改路由; 失败则在 probe/listener/DNS/WinDivert之前停止.

#### 驳斥三: “TTL=60时 Dnscache约每30秒主动刷新每个缓存域名”

不同意. Microsoft文档描述客户端先检查本地缓存, 缓存未命中时再查询 DNS, 并按 TTL老化记录; 审计没有给出官方来源或 VM实测证明 Dnscache会为每条 TTL=60记录固定每30秒主动刷新. 将该说法写入验收预期可能掩盖真实的异常重复查询. v5只接受“应用再次解析或缓存过期后可出现新查询”, 不规定固定30秒后台刷新. 参考: [Microsoft DNS queries and lookups](https://learn.microsoft.com/en-us/windows-server/networking/dns/queries-lookups).

#### 驳斥四: “`TcpClient.ConnectAsync()`才可精确实现500ms语义”

不同意其排他性和“精确”措辞. `ConnectAsync`返回 task, 但 Windows PowerShell 5.1常见 .NET Framework API面仍需要调用方自行等待、分类超时并释放 socket; timeout后的调度和清理可使实际墙钟略超阈值. `BeginConnect`/wait handle等也可构造有界等待, 所以不是只有一个 API可实现. v5选择 `ConnectAsync` + `Task.Wait(timeoutMs)`是为了固定一种可测试实现, 并明确500ms是判定阈值而非绝对总耗时承诺. 参考: [Microsoft TcpClient.ConnectAsync](https://learn.microsoft.com/en-us/dotnet/api/system.net.sockets.tcpclient.connectasync).

#### 驳斥五: “inbound风险由项目负责人已接受的宿主安全假设覆盖”

不同意. 项目负责人明确说主机监听脚本、监听端口和主机侧安全不由本方案管理, 这只是范围排除, 不等于声明宿主可信或风险已被控制. v5把 inbound返回流量列为范围外但未缓解的残余风险, 不会声称已被 FakeNet或某个未确认的宿主假设覆盖.

#### 驳斥六: “Windows 10/Python 3.13/PyDivert 2.1.0组合证据链完整”

不同意. 现有目标 VM日志能证明 Windows 10 `10.0.19045`和 Python 3.13运行, 但没有在同一证据中记录已安装 PyDivert精确版本. 另一份审计中的 PyDivert 2.1 filter helper结果不能自动与该 VM日志合成为完整运行组合证明. PyPI wheel哈希/内容只能证明交付物身份和静态 API候选, 不能证明目标 VM的驱动加载、packet元数据、send/reinject与清理行为. 因此 v5将 `pydivert==2.1.0`降为经静态复核的交付候选, 必须在干净 VM中全量验证. 参考: [PyDivert 2.1.0](https://pypi.org/project/pydivert/2.1.0/).
