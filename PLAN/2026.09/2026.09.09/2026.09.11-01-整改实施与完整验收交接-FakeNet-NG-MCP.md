## 2. 总执行顺序及共同通过规则

执行顺序：H0 对账 → H1/H2 产品整改 → H3 runner/证据链自评 → H4 固定源码与构建 → H5 环境准备 → H6 完整原生矩阵 → H7 双向追溯及作者自评 → H8 独立复核。各项可以交叉补测试，但不能绕过前置资格或用旧候选凑新候选计数。

每次状态变更执行“写入意图 → 执行 → 验证实际结果 → 持久化检查点”。同一动作已有匹配 HEAD、包、身份和证据时复用，不盲目重复。代码修复后的新候选必须明确哪些结果失效、哪些按契约可复用；最终原生发布门禁和 100+50 使用同一最终候选。

以下是所有任务的共同条件：

- 单项 60 秒、incident 全过程 180 秒、同时活动临时磁盘总量 512 MiB 不变，包含启动、准备、读写、校验、发布和清理；不可为测试过关扩预算。
- 同一逻辑 run/attempt 任意时刻真正采集执行者至多 1；只有固定不超过 16 KiB 的协议握手可并行，仍归共同预算、截止、资源与清理责任。不允许排队、任意命令/路径、无 Job fallback 或第二常驻服务。
- 不在 HTTP、状态或编排锁内等待潜在阻塞 I/O。到期先撤销成功资格；迟到成功、文件或 ACK 不能恢复授权。
- 每个对象实际结束后才释放它所需的句柄；助手结束不代表目标或树结束。全部对象结束并全审计通过后，才能解除整体 failed/draining、needs_recovery、资源责任及 start/restart/升级/卸载禁令。已结束对象不必为了审计继续保留句柄。
- 仅有原生证据足以证明 Windows 内核/驱动取消或终止无法完成时，才进入已批准的平台阻断分支。普通超时、实现缺陷、用户态挂起或未知异常不能享受豁免。平台阻断不计成功样本、不使 ACC 通过、不关闭 CHK。
- GUI/独立 CLI 保持原行为，不扩展 MCP 排除范围；配置寻址、重启身份继续当前契约。不得从旧轮次、被否决方向或接手者新建议扩张需求。
