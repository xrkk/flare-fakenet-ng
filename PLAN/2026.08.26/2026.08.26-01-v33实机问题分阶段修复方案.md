## 0. 目的、问题和边界

本方案在同一份分阶段修复方案内处理两个相互独立、分别实施和验收的问题：

1. **P-STOP：停止耗时。** diagnostic-03 已证实 GUI 在停止回调内立即显示反馈，GUI 自身没有额外延迟。总退出约 24.2 秒由两段独立延迟叠加：HTTPListener80 被未完整 HTTP 请求阻塞约 6.4 秒；Python 子进程 `rc=0` 后，PyInstaller one-file 父进程因 `_MEI` 中的 `WinDivert64.sys` 删除失败执行 15 次、每次 1 秒的重试，约 16.0 秒后才返回顶层进程句柄。现象、位置、根因和实现方向均已闭合。
2. **P-SINK：目标 TCP/UDP 未真实到达 Ubuntu。** 非放行域名已正确解析为 `192.168.204.1`，但 TCP 被 Windows 本地 FakeNet 接管，UDP 被策略丢弃；Ubuntu Sentinel 没有收到 target nonce。根因是 v33 有意删除 `ALLOW_TAKEOVER_SINK`，且当前裁决链没有精确 sink 放行分支。

两个问题共享 v34 构建和 VM 验收阶段，但不得共享根因、实现断言或通过结论。P-STOP 通过不能替代 P-SINK，反之亦然。

本方案不处理 GUI 配置写入缺陷：本次实际 INI、GUI 日志、核心日志及 hash 一致，核心出现 `DOMAIN_TAKEOVER_READY`，原疑似 GUI→INI→核心事实丢失未复现且被当前对照证据反驳。diagnostic-03 的 `127.0.0.1:53` 直接探针超时也不作为新产品问题：同一会话的 Windows 系统解析已正确得到 `192.168.204.1`，且 P-SINK 的失败由裁决日志直接解释。也不处理 Linux FakeNet 功能对等、多机协调、自动故障转移、远程管理 Ubuntu、HTTPS 中间人、DoH 解密、一般代码清理或主动式架构治理。

### 1.4 根因结论与排除项

**P-STOP 已证实根因链：**

1. runner 在停止前建立并保留到 `198.51.100.10:80` 的 TCP 连接，只发送未完成 HTTP header；v33 将其重定向到 HTTPListener80。单线程 handler 正在 10 秒读超时内，`shutdown()` 因而等待约 6.4 秒。
2. Python 子进程完成全部 provider、网络恢复和 `rc=0` 后退出；one-file 父进程开始删除 `_MEI59522`。
3. 删除明确失败的文件是 `pydivert\windivert_dll\WinDivert64.sys`。bootloader 找不到可从自身卸载的 `_MEI` DLL，随后执行 15 次 × 1 秒重试仍失败，最终留下 `_MEI` 并退出。
4. GUI 只是在等待真实顶层句柄；反馈为 0.000s，句柄返回后的 UI 调度仅约 31ms，因此 GUI 不是延迟来源。

准确边界是：已证实一次性 `_MEI` 清理与 WinDivert 驱动文件生命周期不兼容；尚未识别 Windows 内核中究竟哪个对象持有文件锁。修复不需要该锁持有者身份，因为固定 onedir payload 不再把驱动文件当作每次会话退出时必须删除的临时文件。

**已排除方向：**不改为多线程 server；不降低正常 HTTP read timeout；不使用 daemon handler；不修改 PyInstaller 的重试常数；不忽略删除错误；不使用固定 `_MEI` 临时目录；不强制卸载驱动；不提前关闭 GUI 句柄；不强杀。

**P-SINK 已证实根因链：**系统 DNS 已产出 `192.168.204.1`；同一 Ubuntu 服务 preflight TCP/UDP 正常；核心裁决把 TCP 记为 `DIVERT_FAKE`、UDP 记为 `DROP_EXTERNAL`；Sentinel 无 target nonce；代码和反向契约测试与实测一一吻合。路由、Ubuntu listener、DNS 未启用、GUI 配置未保存均被排除。

**待核实但不阻断本方案：**同次核心日志还包含 `Failed getting registry value NameServer`、`OpenService failed for Dnscache`、`Failed to call CloseServiceHandle` 和若干 loopback DNS `Inbound capture reinjection failed: WinError 592`。系统 DNS takeover 实际成功、停止健康、DNS/route 前后恢复，且这些事件不能解释当前 P-STOP 或 P-SINK 裁决链，因此本方案不把它们认定为第三个已证实问题。若后续出现可复现的 DNS 失败或恢复差异，应另转反应式调查。

## 2. 固定目标行为

### 2.1 停止行为

SRC-REQ-002 和 SRC-REQ-004 共同固定停止行为：

1. 停止必须完成 listener、Diverter、PCAP、报告、DNS/适配器恢复和正常退出；不得以 daemon 泄漏、强杀、吞错、提前关闭进程句柄或把 `rc=0` 日志当作实际进程已退出来伪造成功。
2. 计时起点为 GUI 停止回调接收点击的单调时钟时刻；GUI 在 1.0 秒内显示明确“正在停止”状态。
3. 同一起点后 5.0 秒内，GUI 持有的 Windows `fakenet.exe` 顶层进程句柄必须返回且退出码为 0，并同时满足第 1 项全部正确性条件。
4. 在同一隔离 VM 快照基线上执行 3 次互相独立的完整策略会话，3 次全部通过才算达标。
5. HTTP 正常请求的串行处理语义和现有 read timeout 不变。停止边界只打断当时仍未完成的活动 transport；没有活动连接、完整 header、完整/不完整 body、对端已关闭、重复 stop、HTTP 与 HTTPS 都必须安全。

### 2.2 Ubuntu sink 行为

1. `ExternalTakeoverIPv4=192.168.204.1` 的唯一含义是 Ubuntu 私网分析主机真实地址。
2. 非放行域名 A 查询继续合成该地址；放行域名、通配域名和真实受控出口不变。
