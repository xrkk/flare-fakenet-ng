## 0. 结论

当配置为`DumpPackets: Yes`时，FakeNet-NG应在抓包过程中同步生成两个PCAP文件，操作者无需执行停止后转换命令：

```text
<prefix>_<timestamp>.pcap
<prefix>_<timestamp>-converted.pcap
```

- 第一个文件保持现有`DLT_RAW`格式和现有文件名，记录裸IPv4/IPv6包；
- 第二个文件使用`DLT_EN10MB`，在每个被接受的相同裸IP包前添加合成Ethernet头；
- 两个文件的记录数量、顺序、时间戳和IP payload必须逐条一致；
- `DumpPackets: No`时不生成任何一个文件；
- 不引入Scapy，使用项目已有的`dpkt`和Python标准库；
- 正常捕获不改变既有网络裁决、重定向、DNS、route或listener行为；新增明确的PCAP健康/拒绝日志，capture-fatal时当前被拦截包按平台显式失败处理并由主线程恢复网络。

这是核心热路径、跨线程fatal传播和跨平台停止生命周期变更，整体风险等级为**高**。必须完成第三方审核和Windows/Linux真实环境验收后才能实施或交付。

## 1. 需求与非目标

### 1.1 明确需求

1. FakeNet-NG写入PCAP时直接同步写入原始版和非裸IP版；
2. 原始文件必须保留，不能只输出Ethernet版本；
3. 不要求操作者执行额外转换步骤；
4. 两个文件必须来自同一次抓包、同一条写入路径；
5. Windows和Linux均纳入设计与验收。

### 1.2 非目标

本方案不包含：

- PCAPNG转换或pktmon ETL转换；
- 对已有PCAP文件执行离线批量转换；
- 添加、删除或改变任何网络放行规则；
- 自动开启当前配置中关闭的`DumpPackets`；
- 修改FakeNet-NG当前“初始包/修改后包可能各写一条记录”的语义；
- 根据进程、方向或接口生成真实二层MAC地址；
- 引入Scapy、Npcap或额外wheel；
- 添加可由生产配置或命令行触发的writer故障测试开关；
- 在宿主机运行FakeNet-NG进行验收。

当前公网IPv4、域名allowlist和takeover配置均为`DumpPackets: No`，本方案不会自动改成`Yes`。这些已审核策略继续使用独立pktmon PCAPNG作为验收证据。

## 2. 当前实现基线

当前实现位于：

- `fakenet/diverters/diverterbase.py::parse_diverter_config`：当`DumpPackets`启用时创建一个`dpkt.pcap.Writer`，linktype为`DLT_RAW`；
- `fakenet/diverters/diverterbase.py::write_pcap`：在`pcap_lock`内同步调用一次`writepkt(pkt.octets)`；
- `fakenet/diverters/windows.py::stopCallback`：关闭单个writer；
- `fakenet/diverters/linux.py::stopCallback`：停止NFQUEUE后关闭单个writer；
- `fakenet/configs/default.ini`和`debug.ini`：默认启用`DumpPackets`；
- domain allowlist、takeover、reviewed IPv4及burp配置：关闭`DumpPackets`。

需要保留的现有合同：

1. 原始PCAP文件名不变；
2. 原始PCAP继续使用`DLT_RAW`；
3. `pkt.octets`的字节内容不变；
4. 初始包和被FakeNet修改后的包按现有调用次数分别记录；
5. `DumpPackets: No`完全不触发文件创建和写入；
6. Windows/Linux停止时仍可靠恢复各自网络状态。

需要显式披露的兼容变化：

1. 当前dpkt writer隐式写入`SnapLen=1500`；v1将两个文件显式写入`SnapLen=262144`，因此原始RAW文件的PCAP全局头会变化，但linktype、记录字节、记录顺序、时间精度和文件名保持不变；
2. 当前未知IP version可能进入RAW文件；v1为维持双文件逐条对应，会把空包和未知version同时拒绝于两个文件之外并计数；
3. 当前同秒同前缀启动使用`wb`可能覆盖旧文件；v1改为原子拒绝覆盖。
4. FakeNet主循环等待周期由当前1秒改为最长100毫秒；该控制面变化也作用于`DumpPackets: No`，用于把capture-fatal响应上界控制在约100毫秒，代价是空闲主循环每秒最多增加约9次唤醒。

## 3. 输出合同

### 3.1 文件名

沿用一次捕获的同一时间戳：

```text
原始：      <DumpPacketsFilePrefix>_<YYYYMMDD_HHMMSS>.pcap
Ethernet：  <DumpPacketsFilePrefix>_<YYYYMMDD_HHMMSS>-converted.pcap
```

原始文件名保持兼容。新增文件固定使用`-converted.pcap`后缀；该命名已通过只读核对仓库外文件`D:\_\code\vpb\modules\src\domains\malware_work\malware_work.py::MalwareWorkHelper.fakenetng_convert()`的当前实现，但不属于本仓库可独立证明或锁定版本的合同，必须由项目方/第三方在实施前再次确认。这里的`converted`只表示链路类型已封装，不表示停止后离线转换。

若任一目标文件已存在，启动直接失败；不覆盖、不自动加序号、不选择其他目录。

### 3.2 PCAP全局头

- 原始文件：使用`dpkt.pcap.DLT_RAW`；在方案锁定的Windows/Linux、dpkt 1.9.8上实际全局头linktype为12，不得为迎合测试改写成101；
- Ethernet文件：`DLT_EN10MB`；
- 两个writer均显式使用`snaplen=262144`和dpkt默认微秒时间精度；
- `262144`只改变PCAP全局头的捕获上限声明，不引入预分配或内存缓冲；正常WinDivert/NFQUEUE IP记录及增加14字节后的Ethernet记录均必须小于等于该值；
- 任一待写记录超过`snaplen`属于捕获基础设施错误，必须在任一文件写入前进入受控fatal，不得写出全局头与记录长度自相矛盾的PCAP；
- 不生成PCAPNG。

v1不保留dpkt隐式的`snaplen=1500`，因为接近MTU的1500字节RAW记录增加Ethernet头后为1514字节，会超过全局头声明。该兼容变化必须由第三方明确审核。

### 3.3 Ethernet记录

对每条原始记录：

```text
Ethernet记录 = 14字节合成Ethernet头 + 原始IP记录完整字节
```

合成地址固定为本地管理地址：

```text
源MAC：02:00:00:00:00:01
目的MAC：02:00:00:00:00:02
```

不从操作系统、接口或数据包方向推断MAC，避免引入平台差异和虚假的真实设备归属。

EtherType由本次写入前取得的不可变原始字节快照首字节的IP version确定：

- IPv4：`0x0800`；
- IPv6：`0x86DD`；
- 已知version但IP头截断：仍按首字节version同步写入两个文件，不做会改变现有RAW捕获范围的完整IP语义校验；
- 空包或其他version：不写入任一文件，增加`rejected_input_count`并输出限速的`PCAP_DUAL_PACKET_REJECTED`；这不是writer故障，不触发FakeNet停止；
- 超过显式snaplen的记录：在写入任一文件前进入受控fatal。

该策略避免恶意样本仅凭未知version终止FakeNet，同时保证两个文件的记录集合始终一致。空包在现有`PacketCtx`构造中通常已被拒绝，但writer仍必须独立防御。

### 3.4 逐条一致性

每次`write_pcap`只取得一次`bytes(pkt.octets)`快照并交给双writer模块；模块在一个内部锁内完成输入裁决、Ethernet构造、单一时间戳获取和两个writer顺序写入。验收必须证明：

1. 两个文件记录数相同；
2. 第N条记录时间戳相同；
3. Ethernet第N条记录去除14字节头后，逐字节等于RAW第N条记录；
4. IPv4/IPv6 EtherType正确；
5. 现有初始包/修改后包的相对顺序不变。
6. 空包/未知version在两个文件中均不存在，拒绝计数和限速日志可追溯；
7. 已知version的截断包仍在两个文件中逐条对应；
8. 两个文件全局头的snaplen均为262144，且所有记录`caplen`不超过该值。

## 4. 设计方案

### 4.1 深writer模块及唯一接口

新增内部模块：

```text
fakenet/diverters/pcapwriter.py
    DualPcapWriter
    PcapWriteError
    PcapCloseSummary
```

`DualPcapWriter`是一个深模块，外部接口仅包含：

- 初始化：接收两个已确定路径、logger，以及仅供测试注入的clock/writer factory；
- `write_ip_packet(raw_bytes)`：同步处理一条不可变IP字节快照；
- `close()`：幂等关闭并返回`PcapCloseSummary`。

文件原子创建、内部锁、输入裁决、snaplen检查、Ethernet封装、时间戳、双写顺序、成功/拒绝计数、永久失败状态、限速日志和双close全部隐藏在模块实现中。`DiverterBase`不得自行构造Ethernet头、持有writer锁或分别操作两个dpkt writer；Windows/Linux不得复制任何封装算法。

`DiverterBase`只持有一个`dual_pcap`和平台共用的capture-fatal状态。`self.pcap`、`self.pcap_lock`作为现有内部字段被移除属于兼容变化；实施前必须检索仓库内调用方，第三方需判断是否为仓库外派生类保留只读迁移属性，但不得提供可绕过双写的`writepkt`兼容入口。

### 4.2 初始化与完整生命周期

PCAP文件不得继续在`parse_diverter_config()`或Diverter构造期间打开。构造函数只解析并保存配置，避免后续平台构造失败时泄漏文件句柄。

当且仅当`DumpPackets: Yes`，`DiverterBase.start()`在任何包处理线程可见writer之前：

1. 计算一次时间戳和两个确定文件名；
2. 分别使用`open(path, 'xb')`原子拒绝已存在目标，不采用“先exists再wb”的竞态写法；
3. 显式以`snaplen=262144`创建RAW和Ethernet writer；
4. 两者都成功后才发布完整`dual_pcap`；
5. 随后才调用平台`startCallback()`启动WinDivert/NFQUEUE；
6. writer初始化失败时，独立关闭所有已打开句柄，并只删除本次调用创建的文件；
7. 平台启动失败时必须先完成平台网络回滚，再关闭writer；若尚无成功记录则删除本次新建的两个仅含全局头文件，若已有任一记录则保留两个部分文件并标记启动失败。

第6、7项是启动事务回滚和证据保留，不是运行时fallback。删除必须依据逐文件`created_by_this_start`标记，禁止依据宽泛路径、glob或文件名猜测。

### 4.3 写入及输入裁决

`DiverterBase.write_pcap(pkt)`保持现有调用位置，且只做以下操作：

1. 若`dual_pcap`不存在，直接返回；
2. 取得一次`bytes(pkt.octets)`不可变快照；
3. 调用`dual_pcap.write_ip_packet(raw_bytes)`；
4. 快照构造或模块I/O异常均进入同一个capture-fatal登记路径。

`DualPcapWriter.write_ip_packet()`在一个内部锁中：

1. 若模块已关闭，抛出新的`PcapWriteError`；若已永久失败，重新抛出首次保存的`PcapWriteError`但不重复记录critical事件；两种情况均不得静默返回；
2. 空包或首字节version不是4/6时，对两个文件均不写，增加一次`rejected_input_count`并限速记录事件；
3. version为4/6时仅据首字节选择EtherType，不对完整IP头长度作额外拒绝；
4. 构造Ethernet记录并在任一写入前校验RAW和Ethernet记录均不超过262144；
5. 获取一个`time.time()`时间戳；
6. 按固定顺序先写RAW、再写Ethernet，并把同一显式`ts`传给两个dpkt writer；
7. 分别维护调用成功计数；任一I/O失败立即把整个模块永久标记失败并抛出`PcapWriteError`。

不增加异步队列、后台批量写入、每包flush、丢包策略或采样策略。空包/未知version的对称拒绝是输入裁决，不是I/O失败或fallback。

### 4.4 capture-fatal传播与唯一停止所有者

`DiverterBase`新增线程安全的`_capture_failure_event`、首个异常保存槽和“一次性记录”锁。数据面线程发生`PcapWriteError`时：

1. 只保存第一个异常并记录唯一`PCAP_DUAL_WRITE_FAILED` critical事件；
2. 将双writer置为永久失败，后续线程不得写任一文件；
3. 设置capture-fatal事件，并令Windows的`_stopping`进入停止态，避免policy watchdog并发执行另一套恢复；
4. 当前被拦截包不再重注入；Linux回调必须给当前NFQUEUE包显式drop verdict，不能无verdict返回并占住队列；
5. 数据面线程不得调用`Fakenet.stop()`、平台`stopCallback()`或恢复网络。

Windows policy的通用`policy_exception`必须显式排除并重新抛出`PcapWriteError`；legacy Windows和Linux队列包装层必须把异常登记为同一capture-fatal状态。

FakeNet主循环每次等待最长100毫秒，同时检查stop flag和capture-fatal事件。100毫秒是在capture-fatal快速恢复与空闲CPU唤醒之间的固定折中：相较现有1秒sleep，最坏检测延迟缩短约900毫秒，空闲时每秒最多增加约9次唤醒。发现capture-fatal后设置进程退出码1，并由主线程作为唯一所有者执行一次完整`Fakenet.stop()`。capture-fatal路径必须增加Fakenet/Diverter的幂等停止门闩，防止finally、启动回滚或重复Ctrl+C二次停止。

运行时部分文件始终保留。禁止单writer继续、自动换目录、内存缓存、异步补写或离线转换补齐。

### 4.5 停止、网络恢复与线程竞态

正常停止维持现有对外行为。capture-fatal停止必须优先释放网络拦截，不得先执行可能耗时或失败的HTML报告生成：

1. 主线程标记全局停止并暂停策略listener；
2. Windows关闭WinDivert handle以唤醒接收线程；Linux先通知所有NFQUEUE线程停止并移除本次添加的规则；
3. 等待所有可能进入`write_pcap`的线程结束，并显式检查线程退出状态；
4. 无论线程停止、报告生成或writer关闭是否失败，都通过独立`try/finally`完成Windows DNS/route恢复和Linux DNS/iptables恢复；
5. 只有确认所有writer调用线程已退出，才调用`DualPcapWriter.close()`；
6. capture-fatal路径在网络恢复和writer关闭后才执行best-effort报告；报告失败不得覆盖原始capture错误或阻止退出；
7. 汇总全部停止错误，最终退出码只要任一capture、线程、恢复或close失败即不得为0。

Windows现有5秒join后必须检查`is_alive()`。若线程仍存活，禁止与其并发关闭writer；记录`PCAP_DUAL_THREAD_STOP_TIMEOUT`、优先恢复网络并以非零退出，writer由进程终止时关闭，产物明确标记不完整。

Linux的`LinuxDiverterNfqueue`必须增加可观察的线程退出/异常状态；不能继续使用“异常静默终止”或无限join而主循环不知情的合同。对停止超时的安全解绑定策略必须在隔离Linux动态测试中证明，无法证明则属于实施阻碍，不能宣称完整落地。

### 4.6 关闭、缓冲与证据边界

`DualPcapWriter.close()`在内部锁中幂等执行，并对RAW、Ethernet两个writer分别尝试close；第一个close失败不得跳过第二个。summary至少包含：

- 两个文件名；
- 两个成功write调用计数；
- `rejected_input_count`；
- 首次写入错误；
- 两个flush/close结果；
- 总体健康状态。

线程停止超时、网络恢复结果、报告结果和最终退出码不属于writer模块，必须由`DiverterBase/Fakenet`在更高层的停止汇总中记录，禁止反向塞入`PcapCloseSummary`破坏模块职责。

`PCAP_DUAL_SUMMARY`中的计数仅是运行时诊断，不得宣称等同于磁盘文件完整。dpkt/Python文件缓冲可能使磁盘满等错误延迟到close暴露；不做每包flush或fsync。正常/故障验收必须在进程停止后用独立解析器重新打开到EOF，验证两个文件的全局头、实际记录数、时间戳和payload。

掉电、强杀和硬件未报告写缓存仍无法保证跨文件原子一致；该限制继续作为明确的不可消除边界。

## 5. 配置与兼容策略

本方案不新增操作者必须填写的配置项：

- `DumpPackets: Yes`：始终生成两个文件；
- `DumpPackets: No`或字段未启用：生成零个文件。

这是对已有`DumpPackets: Yes`输出数量的行为变更：由一个文件变为两个。原始文件名、linktype和记录内容保持不变，但PCAP全局头的snaplen由隐式1500变为显式262144；精确引用原文件名且不校验原snaplen的脚本继续工作。使用`*.pcap`宽泛枚举且假设只有一个文件的脚本可能受到影响。第二个文件沿用现有手动转换方法的`-converted.pcap`命名，不同时生成`-ethernet.pcap`别名。

不提供“只生成RAW”的新开关，也不提供生产故障注入开关，因为这会偏离本次明确目标并增加配置组合。若第三方认为必须保留单文件模式，应退回方案并由项目负责人明确选择，不能由实施者自行添加。

## 7. 测试设计

### 7.1 单元与合同测试

至少覆盖：

1. Windows/Linux、dpkt 1.9.8下，IPv4 RAW与Ethernet文件linktype分别等于`dpkt.pcap.DLT_RAW`（实际值12）和`dpkt.pcap.DLT_EN10MB`（实际值1）；测试不得断言101，也不得驱动生产代码把RAW改成101；
2. IPv6 Ethernet EtherType为`0x86DD`；
3. RAW payload与剥离Ethernet头后的payload逐字节一致；
4. 两个文件的记录数、顺序、时间戳一致；
5. TCP、UDP、ICMP及IPv4分片payload不被改变；
6. 现有初始包/修改后包双写次数一致；
7. 两个PCAP全局头snaplen均为262144，1500字节RAW包对应1514字节Ethernet记录且可正常解析；
8. 已知version截断包仍双写，并可由独立dpkt reader读取到EOF；空包和未知version均不写、计数一致且不触发fatal；
9. RAW或Ethernet记录超过snaplen时在任一写入前fatal；
10. 任一目标已存在时通过`xb`拒绝覆盖，TOCTOU竞态测试不能覆盖旧文件；
11. 第二个writer初始化失败时关闭句柄并只回滚本次新建文件；
12. 平台启动失败发生在零记录和已有记录两种状态时，分别验证删除空头文件与保留部分证据；
13. RAW写失败和Ethernet写失败均禁止单writer继续；
14. buffered write成功但close/flush失败时，两个close仍分别执行并最终非零退出；
15. runtime失败只记录一次critical事件，主线程只执行一次stop并最终非零退出；
16. Windows policy异常分支不吞`PcapWriteError`，legacy线程和Linux NFQUEUE线程均能唤醒主循环；
17. Windows线程join成功/超时、Linux队列线程异常/停止路径均有合同测试；
18. `close()`和stop可重复调用且不会二次关闭或二次恢复；
19. `DumpPackets: No`不创建文件且现有四个已审核策略配置保持No；
20. Windows/Linux恢复逻辑在write、close、报告生成和线程停止失败路径均执行；
21. 正常关闭后用独立reader读取到EOF，验证实际磁盘记录而非仅比较内存计数；
22. 原有完整Python测试全部通过。

故障注入使用模块的内部测试seam和内存/临时writer。端到端VM测试launcher在进程内替换writer factory，分别在第N次RAW写、第N次Ethernet写和close时抛出受控异常；不得修改生产INI、环境变量合同或添加命令行故障开关，也不依赖填满真实磁盘。

### 7.2 性能测试

在同一临时卷、同一锁文件安装出的dpkt 1.9.8和同一Python进程模型中，建立直接使用现有dpkt RAW writer的单writer基线与`DualPcapWriter`对照。harness启动时必须断言并记录dpkt实际版本、模块路径和`DLT_RAW`实际值；生产代码不提供单writer模式，基线仅存在于benchmark harness。

固定数据集分别为100000条64字节IPv4记录和100000条1500字节IPv4记录；每组先进行10000条不计时预热，再独立运行3次并取中位数：

- 记录总包数、总字节、耗时、CPU和输出大小；
- 双文件记录数必须等于输入记录数；
- 不允许因性能压力静默丢记录；
- 双写总输出空间预期接近原始捕获的两倍，并增加每包14字节Ethernet头；
- 双writer中位耗时不得超过同组单writer中位耗时的2.5倍；
- 测试前记录可用磁盘空间，必须足以同时保留本轮全部输出，磁盘空间不足时结果无效而不是判定性能失败；
- 性能结果写入原方案末尾的实施核实记录，并保留机器、Python、dpkt、卷类型和三次原始结果。

不设跨硬件绝对吞吐阈值。若2.5倍相对门禁失败，不得以异步队列、采样或单writer降级绕过；必须更新方案并重新审核。

## 8. 风险与副作用

| 风险 | 等级 | 说明与控制 |
|---|---|---|
| WinDivert/NFQUEUE热路径同步I/O增加 | 高 | 双写增加锁持有、复制和磁盘写入；固定数据集的中位耗时不得超过单writer的2.5倍 |
| 磁盘空间接近翻倍及延迟报错 | 中至高 | 文档明确两个完整捕获文件；缓冲错误可能到close才出现，不自动删除原始文件 |
| 两个文件运行时部分不一致 | 高 | 预构造后双写、计数、fatal状态、非零退出；不宣称磁盘错误下可原子写两个文件 |
| 写入/超长记录失败影响FakeNet持续运行 | 高 | 选择受控停止而不是无抓包继续；第三方必须确认该取舍 |
| Windows恢复遗漏 | 高 | writer异常必须透传到主循环并进入既有stop/restore |
| Linux iptables/DNS恢复遗漏 | 高 | 恢复必须置于不被writer关闭异常跳过的finally结构 |
| Windows线程停止超时后close竞态 | 高 | 活线程存在时禁止close writer，优先恢复网络、非零退出并标记文件不完整 |
| Linux回调异常导致队列停滞或无限join | 高 | 明确drop verdict、线程状态和有界主循环唤醒，必须真实Linux验证 |
| 空包/未知version被用作反分析终止触发器 | 中 | 改为对称拒绝和计数，不触发fatal；已知version截断包仍保留 |
| RAW文件snaplen全局头变化 | 中 | 显式从1500改为262144，记录内容不变；文档和合同测试披露 |
| IPv6被错误标记IPv4 | 中 | 依据首字节version选择EtherType，独立测试 |
| 现有脚本宽泛匹配`*.pcap` | 中 | 原文件名不变，新增`-converted`后缀；文档提示并检索仓库内调用方 |
| 文件名同秒碰撞 | 中 | 两个目标任一存在即启动失败，不覆盖或自动改名 |
| 合成MAC被误认为真实设备 | 低至中 | 使用固定本地管理MAC并在文档明确其仅用于封装 |
| 新模块漏入安装/交付包 | 中 | wheel/源码安装及builder归档合同验证模块存在 |
| 仓库外代码依赖`self.pcap` | 中 | 仓库内检索并披露字段移除；禁止保留可绕过双写的单writer入口 |
| 已验收策略控制面行为被意外改变 | 低至中 | `DumpPackets: No`避免双写I/O，但100毫秒主循环等待和幂等停止门闩仍作用于共用控制面，必须回归stop flag、Ctrl+C、日志排空和正常网络策略 |

### 8.1 无法完全消除的边界

两个普通文件之间不存在跨文件原子写入。掉电、进程强杀、磁盘硬错误或未报告的硬件写缓存可能造成尾部记录数不一致。受控I/O/close错误可通过日志和非零退出识别；掉电和强杀可能来不及记录任何错误。因此内存计数不能证明磁盘完整，本方案也不能声称在硬故障下保证两文件原子一致。第三方必须确认该边界是否可接受。

## 9. Fallback声明

本方案**没有添加未显式请求确认的运行时fallback**。

明确禁止：

- 双写失败后退化成RAW单写；
- 双写失败后退化成Ethernet单写；
- 切换到其他目录或自动改文件名；
- 自动丢包、采样或进入异步队列；
- 自动调用离线转换补齐文件；
- 使用Scapy作为`dpkt`失败后的备用实现；
- 自动开启已关闭的`DumpPackets`。

初始化失败时删除本次启动刚创建且没有成功记录的文件属于事务回滚；运行时失败后保留部分文件并受控停止属于显式失败处理，均不是替代成功路径。空包/未知version对两个文件同时拒绝是输入裁决，不是单writer降级；测试launcher注入writer factory是测试seam，不可由生产配置触发，也不是运行时fallback。

## 12. 第三方审核重点

第三方至少应重点审核：

1. 是否接受`DumpPackets: Yes`从一个文件变为两个文件，且不提供单文件开关；
2. 是否确认Windows/Linux、dpkt 1.9.8下RAW linktype保持实际值12而不是101；
3. 是否接受RAW文件全局头snaplen由隐式1500变为显式262144，且两个文件统一为262144；
4. 262144上限及超长记录受控fatal是否符合WinDivert、NFQUEUE和下游解析器合同；
5. 同步双写对热路径的影响以及“中位耗时不超过2.5倍”门禁是否合理；
6. 深writer模块是否真正拥有文件、锁、输入裁决、时间戳、双写、计数和close，外部接口是否足够小；
7. 两个文件使用同一显式时间戳、逐条payload一致的实现是否可验证；
8. 已知version截断包保留、空包/未知version双边拒绝且不fatal是否合理，并确认独立reader不会因截断记录阻断后续记录；
9. 固定本地管理MAC是否会对下游工具造成错误语义；
10. `-converted.pcap`兼容既有手动转换命名的同时，是否会破坏已有`*.pcap`枚举脚本；
11. `xb`原子创建、部分初始化回滚、平台启动失败及同秒碰撞处理是否安全；
12. 运行时任一writer或close失败后受控停止而非单writer继续是否合理；
13. fatal事件、首错保存、100毫秒主循环等待和主线程唯一stop所有权是否可能死锁或漏退出；
14. Windows policy通用异常、legacy接收线程和watchdog是否会吞错或并发恢复；
15. Windows线程join超时时不关闭writer、优先恢复网络的取舍是否合理；
16. Linux当前NFQUEUE包显式drop、线程异常可观察性及停止超时合同是否安全；
17. Windows的WinDivert、DNS、route恢复在write、close、报告和线程故障路径是否完整；
18. Linux的NFQUEUE、iptables和DNS恢复在同类故障路径是否完整；
19. dpkt缓冲导致错误延迟到close、内存计数不能证明磁盘完整的边界是否准确；
20. 掉电/强杀下无法跨文件原子一致的边界是否被准确披露；
21. 当前domain allowlist、takeover、reviewed IPv4及burp配置保持`DumpPackets: No`是否得到合同保护；

### 16.9 Windows VM v2执行结果与v3修正（2026-08-05）

用户回传的`dual-pcap-v2-20260805-194020`明文日志已核对。CPython 3.13.7 AMD64、锁定依赖、dpkt 1.9.8、`DLT_RAW=12`以及142项Python测试均通过；四个用例的运行前后DNS/route快照比较也均通过。由于性能门禁和所有FakeNet启动用例均在数据面开始前失败，本次仍不能计为Windows动态验收。

失败事实与原因如下：

1. 性能脚本以`python test\benchmark_dual_pcap.py`运行时，Python把脚本目录作为首要模块目录，仓库根目录不在导入路径，因而报`ModuleNotFoundError: No module named 'fakenet'`；三个故障launcher存在相同问题；
2. 正常用例生成的UTF-8配置包含中文绝对输出路径，而Windows Python 3.13按VM当前GBK默认编码读取配置，产生`UnicodeDecodeError`；
3. runner把`launch.cmd`写成带BOM的UTF-8，`cmd.exe`把首行BOM解释成命令字符并产生`'﻿@echo'`错误；
4. 子进程早退分支在读取`ExitCode`前没有显式`WaitForExit()`和`Refresh()`，VM日志因此记录为空的`exit=`，削弱了诊断证据。

v3修正限定在Windows VM验收层：

Windows动态IPv6门禁未通过，且暴露出审核方案的事实矛盾：默认非domain-allowlist模式在`fakenet/diverters/windows.py`中固定使用`outbound and ip`，不会把IPv6交给双PCAP writer。当前runner的TCP6又使用默认IPv4 `TcpClient`，在发包前即报地址族不匹配；UDP6发往`::1`属于回环，也未进入RAW PCAP，并触发已有ProxyListener在`diverter=None`窗口中的异常日志。因此不能把“正常默认配置实时捕获IPv4和IPv6”继续作为不加生产范围变更即可实现的合同。此项为**高风险设计阻碍**，必须在更新方案中明确选择：扩大Windows生产捕获/处理范围并新增对应安全审核，或把Windows默认模式动态门禁限定为IPv4、由单元/独立writer测试证明IPv6封装合同。不得在未审核前自行选择。
