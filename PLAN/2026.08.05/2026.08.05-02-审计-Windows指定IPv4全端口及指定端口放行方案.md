## 0. 审计概要

本方案在已验收的 v10 takeover 机制上新增静态精确 IPv4 直连规则(`ExternalAllowedIPv4Rules: TCP/IP/PortScope`), 新裁决 `ALLOW_REVIEWED_IP` 置于裁决链第 6 位(DeepSeek relay 重定向之后、legacy Divert 之前), 并配套启动前只读 batch 路由门禁、逐 packet 源地址/InterfaceIndex 复核、运行期路由漂移全局挂起和有界 flow 审计。

审计做四类核实:

1. **代码事实**: v10 基线 `123cfd9` 的裁决链顺序、双域挂起模型(`_egress_suspended`/`_takeover_suspended`)、地址刷新线程(5s 轮询)、takeover 路由快照脚本(`_TAKEOVER_ROUTE_SCRIPT`, 强制 on-link 语义)与方案声明的插入点、优先级、路由合同逐条核对, 全部吻合。
2. **依赖事实**: pydivert 2.1.0 wheel 的 `Packet.interface` 为 `(IfIdx, SubIfIdx)` 元组——逐 packet InterfaceIndex 复核可实施。
3. **测试事实**: 基线 `def test_` 计数 15+24+4+6+1+24+1 = **75**, 与方案 §11.5"现有 75 项"一致。
4. **机制事实**: `ExternalBlockQUIC=Yes` 仅为配置校验标志(egresspolicy.py:162-164), QUIC 阻断是结构性的(无 UDP 放行)——"UDP/IP/443 或 UDP/IP/* 覆盖该 IP 的 QUIC 默认阻断"的语义准确。

**方案相对 v10 的增量风险可控**: 不修改 `DiverterBase` DNS 门禁、不修改 EgressPolicy 构造签名、不触碰 takeover/DeepSeek/Disabled 路径; 全部为插入式分支。

## 2. 发现与不同意见

### F1(中): takeover 子状态挂起与 reviewed-IP 路径的交互合同未定义

- v10 存在两个失败域(egresspolicy.py:356-394): takeover 子挂起(如 takeover IP 变为本机地址, `sink_became_local`)只挂起 sink + takeover DNS; 全局挂起(如 external DNS 进入本机快照、地址刷新整体失败)挂起全部出口。
- 方案 §7.2 规定路由漂移→全局挂起, 但没有规定:**takeover 子挂起时 reviewed-IP 路径是否继续?** 以及:**任一 reviewed IP 在运行中进入本机地址快照时, 应全局挂起还是仅挂起该规则?**
- 建议补两条显式合同: (1) reviewed-IP 路径只受全局挂起和自身路由/源地址/接口漂移影响, takeover 子挂起不影响它(除非触发条件同时影响 reviewed 路由); (2) reviewed IP 进入本机快照→按 `external_dns_server in snapshot` 的现有模式(egresspolicy.py:360-362)做**全局**挂起, 并补对应单元测试。

### F2(中低): 分片检测机制未指定, 现有代码无分片保护

- `fnpacket.py` 的 `_parseIpv4` 用 `dpkt.ip.IP(raw)` 解析且不检查 fragment offset/MF 标志; `_parseIp`(276-277)直接取 sport/dport。对非首片分片, dpkt 若"成功"解析会得到垃圾端口。
- 后果: 对精确端口规则, 垃圾 dport 可能假匹配(安全方向风险低: 孤立分片无法重组交付, 且 `*` 规则无端口条件); 但 matcher 行为随 payload 字节变化, 不可预测, 且与方案 §5"无法取得完整协议/端口信息时失败关闭"的合同不符(合同成立的前提是能识别"无完整信息", 现有代码没有该识别能力)。
- 建议: §5 明确规定 matcher 前置步骤——在构造 `ReviewedPacketTuple` 之前检查 IPv4 头 `off & 0x3FFF != 0`(offset)或 MF 标志, 非首片直接失败关闭, 不进入 transport 解析; 同时把该检查加入 takeover sink 路径(现有 takeover 路径存在同样的潜在垃圾解析问题, 新代码不应继承)。
- 补充: 对 `*` 规则, 非首片失败关闭会破坏大 UDP 数据报(首片命中、后续片被丢, 数据报无法重组)。方案 §17-12 已把该问题列为第三方重点, 建议在精确规则附录中对每条 UDP 全端口或大数据报 UDP 规则注明"分片 UDP 业务不可用"由责任人接受或拒绝。

### F3(中低): 启动路由门禁的源地址判定方法未规定

- `Get-NetRoute` 对默认路由通常返回空 SourcePrefix; 冻结源 IPv4 需要从接口首选地址推断, 而 Windows 实际选源逻辑(接口多地址、多子网)可能与 PowerShell 推断不一致。冻结源与运行期实际 src 不一致时逐 packet 复核会拒绝(安全方向正确), 但可能导致"审核 IP 整体不可用"的可用性问题。
- 建议: §7.1 明确源地址判定方法(SourcePrefix 优先, 否则接口首选地址, 必要时与 WinSock UDP connect 选源交叉核对——该操作不发包), 并把"启动门禁推断源地址 == 该 IP 首个实际出站 packet 的 src"加入 VM 正向验收。

### F4(低): `IP_ALLOW_DOMAIN_OVERLAP` 的检测点未定义

- 检测需要 DNSListener 在 `_validate_and_synthesize`(DNSListener.py:367-438)验证上游 A 记录后与 reviewed IP 集合求交; 需要 facade 新增只读回调(如 `has_reviewed_ip(ip)` 或 `reviewed_ip_rules()`)。方案 §4.3 只说"不扩大 listener facade"、§10 说 diverterbase.py"只增加必要配置识别", 未指明该回调归属。
- 建议: 在 §4.3/§10 明确该只读回调契约(返回不可变集合或布尔判定), 并补单元测试(重叠→仅事件, 不阻断)。

### F5(低): batch 路由复核加入 5s 刷新线程的耗时上限未规定

- 现有 `_refresh_local_addresses`(windows.py:803-852)每 5s 一轮; 增加一次批量 `Get-NetRoute`(最多 16 个 IP)会延长单轮执行时间, 漂移检测上界 = 轮询周期 + 查询耗时。
- 方案已要求"VM 故障注入必须测得实际检测上界"(§7.2), 已覆盖主体; 建议补充一条: 若单轮 batch 查询耗时超过轮询周期一半, 启动器/运行期记录告警并作为验收阻碍处理, 防止轮询周期形同虚设。

### F6(低): `BlackListPortsUDP` 与审核 IP 全端口规则的交互未说明

- 现有配置 `BlackListPortsUDP: 67,68,137,138,443,1900,5355`(legacy 直通语义, 由最终裁决覆盖)。IP 规则优先于 legacy 路径, 因此到审核 IP 的 67/68/137/138/443 等黑名单端口会被 UDP/* 规则直送。
- 这与"全端口=1..65535"合同一致, 不属于缺陷; 但此前审计(02 文档 M10)指出黑名单交互需显式说明。建议 §6 补一句"BlackListPortsUDP 只作用于 legacy 路径, 不影响审核 IP 全端口直送", 并纳入回归测试清单。

### F7(低): `ExternalAllowedIPv4Rules` 的多行写法与 configparser 语义未规定

- §3.1 示例为多行缩进写法; configparser 默认不支持裸多行值, 需要单行或显式续行。建议规定"该字段必须单行, 或多行时必须采用明确的续行策略", 避免解析歧义; 该规则进入纯配置测试。

### F8(低): 重叠 IP 的已建立直连流不撤销

- 当 DeepSeek 域名 DNS 返回某审核 IP 时, 已通过 IP 规则建立的直连流继续存在(无按流撤销机制), 只有新连接才进入 lease/relay 路径。这是 TCP 语义的固有特性, 方案无需改动, 但建议在 §5 或审核重点中注明"规则不按流撤销已建立直连"这一边界, 避免验收时误判。

### F9(低): inbound/ARP 残余边界已准确描述, 无异议

- §2.2/§13 对 inbound 返回流量与二层 ARP 不受 outbound 裁决覆盖的描述准确, 且未夸大为已缓解(验收标准 17)。与 v4 审计 N6 建议一致, 本方案已吸收。

### F10(低): 上限与 manifest 绑定已覆盖, 无异议

- 32 条规则/16 个 IP 上限、规则与配置 SHA 绑定、占位符拒绝、`default.ini` 只加注释(避免"存在但为空"与合同冲突)均设计正确。

## 3. Fallback 复核(v1 添加的 fallback 及合理性)

v1 明确不添加运行时网络 fallback, 经核对包含以下非运行时项:

| v1 中的 fallback/确定性选择 | 性质 | 条件/约束 | 合理性 |
|---|---|---|---|
| 字段完全缺失 → 保持 v10 行为(§14) | 向后兼容默认 | 不启用 IP 放行; 与"存在但为空即失败"区分 | 合理。与 v10 的 takeover 激活判据模式一致(egresspolicy.py:220-225) |
| 路由漂移/路由查询失败 → 全局挂起, 当前进程不自动恢复(§7.2/§14) | 保守失败关闭 | 停止 DeepSeek、IP 直连、takeover 全部发送; 不选备用接口/网关/IP; 不修改路由 | 合理。牺牲可用性换取一致失败关闭; 明确不是替代路径 |
| 逐 packet 源地址/InterfaceIndex 不匹配 → 立即拒绝 | 失败关闭 | 不切换到其他接口 | 合理 |
| 审计表淘汰(4096 项/60s TTL)与 PID 查询失败(§9) | 观测故障隔离 | 只降低可观测性, 不改变授权; 淘汰/归属失败不得扩大或收窄授权 | 合理。不是网络 fallback |
| 不自动解析 hostname、不指定端口失败后扩全端口、不协议降级、不改送 sink/DeepSeek、不热更新/重试(§14) | 无 fallback | — | 合理。均为显式禁止 |

结论: 未发现 v1 添加不合理 fallback, 也未发现漏报的隐式运行时回退。

## 4. 对现有机制的破坏评估

- **增量面收敛**: 仅 `EgressPolicy`(新字段解析/冻结、matcher、route binding)与 `windows.py`(新检查点、batch 路由、flow 审计)两处插入式改动; `DiverterBase` 只增加配置识别, 不扩大 listener facade。
- **优先级无冲突**: 新检查点(第 6 位)在 permit(1)/relay 修复(2)/takeover sink(3)/relay 映射(4、5)之后, 与现有代码顺序一致; 地址空间上 takeover(私网)与审核 IP(公网)不相交, DeepSeek 重叠由优先级合同覆盖。
- **回归保护**: 75 项既有测试计数属实, v10 Ctrl+C/Enter、日志排空、DNS/IP/路由恢复与组合包回归合同(§11.5)覆盖完整; `_refresh_local_addresses` 增加 batch 查询的耗时影响见 F5。
- **v10 已验收模式复用**: 激活判据、route snapshot 校验、发送前二次复核、双域挂起均为 v10 已验证模式, 实施风险低。
- 未发现方案未识别且会破坏现有动态/接管/Disabled 模式的机制性缺陷。

## 6. 审计结论

- **正确性**: 方案对 v10 基线的描述全部与代码事实吻合; 优先级、重叠语义、QUIC 扩展、路由合同分离(on-link vs 默认网关)均正确; pydivert 2.1.0 interface 元数据可用性已实证; 75 项测试计数属实。未发现阻断性错误。
- **完整性**: F1 为中等级合同补强, F2/F3 为中低等级精确化, 其余为低等级补充; 风险表(§13)覆盖完整, 未发现被低估到影响决策的风险。
- **fallback**: 仅含向后兼容默认与保守失败关闭, 无隐式运行时回退, 全部合理。
- **建议流转**: 吸收 F1-F8 中经代码事实复核同意的内容后升版送第三方机制审核, 并与精确规则审核附录一同闭环; 按方案自身门禁, 在两项审核通过且项目负责人明确授权前不得实施。

本审计为只读审计, 未修改代码、配置、启动脚本、测试或交付 ZIP, 未在任何主机或 VM 试运行方案。

## 7. 方案方独立核验回复与驳斥（2026-08-05）

- 回复对象：本文对方案v1的审计意见。
- 处理结果：原方案已升版为v2；F1、F6、F8同意，F9、F10确认已覆盖；F2、F3、F4、F5、F7只接受问题本身，不接受全部建议实现。
- 核验原则：第三方结论不作为事实替代物；以下回复重新对照基线 `123cfd9`，且未运行FakeNet-NG、未加载WinDivert、未执行网络测试。

### R1：驳斥“完全兼容、全部为插入式分支、实施风险低”的确定性结论

**驳斥内容：** 审计概要和破坏评估把静态落点存在进一步推导成“与基线v10代码结构完全兼容”“全部为插入式分支”和“实施风险低”，证据不足，方案方不接受这些表述作为已证明结论。

**驳斥原因：** 新功能至少涉及原始IPv4分片preparse、EgressPolicy状态/索引、DNS settings只读快照、Windows route batch与超时、逐packet InterfaceIndex复核、全局/子状态交互以及有界flow审计。这些改变横跨多个运行期seam。只读代码核对能证明实现可行性和候选插入点，不能证明没有行为回归；兼容性必须由新增单元测试及隔离VM矩阵证明。v2因此继续保留完整审核和VM门禁。

### R2：部分驳斥F2把分片检查扩展到takeover sink

**驳斥内容：** 同意现有 `fnpacket.py`没有显式IPv4分片保护，也同意reviewed-IP路径必须在transport解析前处理；不同意在本功能中“同时把该检查加入takeover sink路径”。同时，审计所述“`off & 0x3FFF != 0`后非首片直接失败”表述不精确：该mask同时覆盖MF首片和非零offset后续片，不能只称非首片。

**驳斥原因：** takeover sink属于已验收v10私网接管机制，顺带修改会扩大未审核回归范围，并可能破坏接管侧大UDP数据报。v2采用严格且范围受控的合同：只要目标IP/协议命中reviewed规则，MF首片或非零offset后续片全部在构造transport tuple前失败关闭；未审核目标、takeover和legacy保持v10行为。既有路径若要统一修复，应另立方案。

### R3：部分驳斥F3的SourcePrefix/Preferred地址选源顺序

**驳斥内容：** 同意必须明确冻结源IPv4的判定方法；不接受“SourcePrefix优先，否则接口首选地址”的推断链作为授权依据。

**驳斥原因：** `Get-NetRoute`结果不能稳定提供可直接作为实际选源的SourcePrefix，接口也可能有多个Preferred地址。基线v10的 `_TAKEOVER_ROUTE_SCRIPT`已经通过无发送UDP socket `Connect`读取Windows实际 `LocalEndPoint.Address`，再验证其属于最佳路由接口。v2沿用这一经代码事实存在的方法，并把任一不一致作为启动失败；VM仍需验证首个真实packet的src/InterfaceIndex与冻结值一致。

### R4：部分驳斥F4建议新增listener callback

**驳斥内容：** 同意 `IP_ALLOW_DOMAIN_OVERLAP`必须在安全验证后的A记录处检测；不接受新增 `has_reviewed_ip`或 `reviewed_ip_rules`单用途callback。

**驳斥原因：** DNS listener的 `_resolve_allowed_a`已调用 `getEgressSettings()`。在该不可变设置快照中增加reviewed-IP到rule-id映射，并把现有settings传入验证/安装后的交集检查，就能完成事件记录。新增一个只做policy转发的方法会扩大浅层interface，降低module depth和locality，且没有第二个独立adapter需求。v2同时明确该事件不阻断DNS、不撤销lease、不改变授权。

### R5：部分驳斥F5“超过半个轮询周期仅告警”

**驳斥内容：** 同意必须给batch route query设定耗时预算；不接受超出预算后仅记录告警并继续出口。

**驳斥原因：** 查询超预算意味着route安全前提在更长窗口内不可确认，仅告警不符合v2失败关闭目标。v2固定5秒刷新周期和2秒query deadline：启动超时直接失败，运行期超时按查询失败全局挂起；VM测量包含线程调度误差的实际检测上界。

### R6：部分驳斥F7对ConfigParser多行示例的事实判断

**驳斥内容：** 不接受“§3.1示例为ConfigParser不支持的裸多行值”这一判断。

**驳斥原因：** 原示例在字段下一行使用缩进，属于Python `ConfigParser`合法continuation，并非未缩进的裸续行。审计提出的维护性风险仍然合理，因此v2明确：支持单行或缩进续行，拒绝裸续行、混入新键、缺失逗号及空项，并加入配置测试；但不能以错误前提要求强制单行。

### R7：其余意见的处置边界

- F1同意：takeover专属子挂起不影响reviewed-IP；reviewed IP进入本机快照触发全局挂起。
- F6同意：reviewed-IP第6位裁决优先于legacy `BlackListPortsTCP/UDP`，并补回归。
- F8同意：已建立IP直连流不因后续DNS重叠追溯撤销；只有新建有效lease/mapping连接进入relay。
- F9、F10同意审计确认，但原v1已经覆盖，不为制造修改痕迹而重复增加合同。

**回复后的流转：** 原方案v2必须重新接受第三方机制复审，精确规则附录也仍需单独审核；两项审核通过并获得项目负责人明确实施授权前，禁止实施。
