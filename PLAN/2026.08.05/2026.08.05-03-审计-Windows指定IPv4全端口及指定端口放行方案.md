## 3. 新发现(v2 特有)

### V2-1(低): fragment preparse 与优先级 1-5 的前置关系未注明

- v2 §5 规定 preparse 发生在"构造 WindowsPacketCtx 和读取 transport 端口前", 即先于 `match_control_flow`(优先级 1)。这意味着: 若允许域名解析出的 DeepSeek 公网 IP 恰为审核 IP(重叠), relay 上游 socket 的 permit 承载流若出现分片, 会被 preparse 先丢弃, 而不是按"优先级 1 permit 优先"处理。
- 实际影响近零(TCP 通过 MSS 协商避免 IP 分片, relay 流量不会分片), 方向安全(失败关闭)。但为封闭"lease/mapping 优先"合同的口径, 建议在 §5 补一句: "fragment preparse 位于优先级 1-5 之前; 对重叠审核 IP 上承载 permit/lease 的分片流量(实践中 TCP 不分片, 影响近零)按 reviewed_ip_fragment 失败关闭", 并视需要补一条测试。

### V2-2(低): "混入新键"的检测规则未给可测试定义

- §3.1 要求"混入新键…失败关闭", 但未规定如何识别。configparser 下未缩进续行会变成一个新的 `[Diverter]` 键, 而 FakeNet 对未知键总体容忍, 单靠 EBNF 值解析无法可靠发现"规则片段被拆成了新键"。
- 建议: 定义可测试规则——当 `ExternalAllowedIPv4Rules` 存在时, `[Diverter]` 中不允许出现其他含 `/` 或可匹配规则语法(`协议/IP/端口`)的键; 并补纯配置测试(裸续行被解析为新键 → 启动失败)。

### V2-3(低): 文档残留 v1 引用

- §12 验收标准第 1 条仍写"v1机制方案与精确规则审核附录均经第三方审核通过"; §13 风险表、§15-7、§16 Phase 0 亦残留 "v1"。其中 §12-1 是验收合同文本, 会引入"审核对象是 v1 还是 v2"的歧义。
- 建议: 统一为 v2(或改为"本方案")后再送复审。

### V2-4(低): 无发送 UDP 选源探测的目标端口未固定

- §7.1 未指定 UDP `Connect` 的目标端口。因无发送, 端口不影响 Windows 选源, 但为 batch 脚本确定性和测试可复现, 建议固定为单一常量端口(如 53 或 9), 写入路由检查脚本合同。

### V2-5(低): 已确认无异议的取舍

- §20.1-2 对 takeover sink 分片语义的保留、§20.1-5 对 deadline 超时的全局挂起, 均与失败关闭原则一致, 且避免破坏 v10 已验收行为; 无需修改。建议在 §11.4 保留"takeover 分片路径不因新增 preparse 改变"的回归断言(已有), 并保持附录对"审核 IP 上分片 UDP 业务不可用"的逐条确认。

| v2 中的 fallback/确定性选择 | 性质 | 合理性 |

## 8. 方案方独立核验回复与驳斥（2026-08-05）

- 回复对象：本文对方案v2的复审意见。
- 处理结果：原方案已升版为v3；V2-1、V2-3、V2-4同意，V2-2部分同意，V2-5确认无需新增机制。
- 额外核验：除基线 `123cfd9`只读代码外，使用Python标准库 `ConfigParser`分别测试未缩进裸续行、缩进续行和option-like规则行；未导入或运行FakeNet-NG。

### R1：部分驳斥V2-2关于“裸续行形成新键”的事实判断

**驳斥内容：** 不接受“configparser下未缩进续行会变成一个新的 `[Diverter]`键”作为一般事实，也不接受据此拒绝所有含 `/` 的未知键。

**驳斥原因：** 标准库实测结果为：

1. `ExternalAllowedIPv4Rules`下一行未缩进且不含option delimiter的 `UDP/IP/Port`触发 `ParsingError`，不会形成新键；
2. 缩进的 `UDP/IP/Port`合法并入原字段值；
3. 只有人为写成 `TCP/IP/Port = stray`时才形成独立option。

因此v3采用范围精确的合同：字段存在时，拒绝规范化option name以 `tcp/`或 `udp/`开头的独立键；不以“任何含 `/` 的键”扩大拒绝范围。这样能捕获option-like误写，又不改变FakeNet对无关未知配置的既有兼容行为。

### R2：驳斥“duplicate key天然失败等同于duplicate rule拒绝”

**驳斥内容：** 不接受审计§1中“重复key天然失败……与§3.2重复规则拒绝合同一致”的等同关系。

**驳斥原因：** `ConfigParser(strict=True)`只拒绝同一section中的重复option name；多个相同rule token完全可以出现在同一个 `ExternalAllowedIPv4Rules`字符串内，ConfigParser不会识别。值内rule规范化、duplicate rule检测与duplicate option检测是两个不同失败层，必须分别实现并分别测试。v3已明确保留两者。

### R3：修正V2-1中的“影响近零”论证

**驳斥内容：** 同意fragment preparse位于优先级1-5之前，但不采用“实践中TCP不分片、影响近零”作为正确性或验收依据。

**驳斥原因：** 分片是否常见不改变interface合同。v3明确：只要目标IPv4/协议命中审核规则，MF或非零offset fragment均先于control-flow permit、relay mapping和有效lease失败关闭；并用预置上述状态的合成fragment测试证明门禁顺序。该行为是有意失败关闭，而不是依赖低概率假设。

### R4：限定“未发现机制性缺陷”的证明力

**驳斥内容：** 对本文“未发现v2会破坏现有模式”“新增技术主张全部成立”的表述，只接受为静态复审结果，不接受为运行期兼容性已经证明。

**驳斥原因：** reviewed-IP fragment preparse、reserved option检测、固定UDP/9无发送选源、route query deadline和状态交互仍涉及运行期seam。只读核对能证明实现路径合理，不能代替单元测试、PowerShell合同测试和隔离VM PCAP证据。v3继续保留这些门禁。

### R5：同意并引入的其余内容

- V2-1核心意见同意：明确fragment门禁位于优先级1-5之前，permit/mapping/lease不能覆盖，并补测试。
- V2-3同意：当前有效合同统一为v3或“本方案”，历史§19/§20保留版本语义。
- V2-4同意：无发送选源固定 `ROUTE_PROBE_UDP_PORT=9`，并要求探测阶段物理接口UDP/9为0。
- V2-5同意：保留takeover/legacy不受新增preparse影响的回归断言及reviewed-IP分片业务附录确认，无需新增机制。

**回复后的流转：** 原方案v3必须重新接受第三方机制复审，精确规则附录仍需单独审核；两项审核通过并获得项目负责人明确实施授权前，禁止实施。
