## 0. 审计概要

方案要求 `DumpPackets: Yes` 时同步生成 RAW(`DLT_RAW`, 文件名不变)与 Ethernet(`DLT_EN10MB`, `-converted.pcap`)两个 PCAP, 由深模块 `DualPcapWriter` 统一持有文件、锁、输入裁决、时间戳、双写、计数与 close; 双写失败进入 capture-fatal, 由主线程唯一停止并非零退出。

审计完成四类核实:

1. **现状事实**: `parse_diverter_config` 构造期建 writer、`write_pcap` 锁内单写、两平台 stopCallback 关闭顺序、DumpPackets 配置分布——全部与代码吻合。
2. **dpkt 1.9.8 源码事实**: 默认 `snaplen=1500` 属实; `writepkt_time` 写 `caplen=len` 且**不截断**(超 snaplen 记录会写出 snaplen<caplen 的不一致文件, 支撑方案 snaplen=262144 的必要性); 微秒时间精度属实; `DLT_RAW = 12`(非 OpenBSD)——**与方案测试合同的 101 不符(F1)**。
3. **版本事实**: `requirements-domain-takeover-windows.lock:9` 锁定 `dpkt==1.9.8`, 与方案性能基准"同一 dpkt 1.9.8"一致。
4. **缺陷识别核验**: 方案 §4.5 针对的三个现有缺陷均真实存在(见 §1 表)。

## 2. 发现与不同意见

### F1(中): §7.1-1 测试合同"RAW 与 Ethernet 文件 linktype 分别为 101 和 1"与 dpkt 事实不符

- dpkt 1.9.8 `pcap.py` 源码: `if sys.platform.find('openbsd') != -1: DLT_RAW = 14 else: DLT_RAW = 12`——在 Windows/Linux 上 `dpkt.pcap.DLT_RAW = 12`, 而 **101 是 libpcap LINKTYPE_RAW 的现代编号**, 不是 dpkt 常量。
- 当前 `diverterbase.py:1086` 使用 `linktype=dpkt.pcap.DLT_RAW`, 实际写入的 linktype 是 **12**(Wireshark 等工具仍识别为 raw IP)。
- 后果: 若测试按方案断言 101, 会失败; 若实现为满足测试显式写 101, 则构成 RAW 文件全局头的**未披露兼容变化**, 与 §2"linktype 保持不变"合同矛盾。
- 建议: 二选一并写入方案——(a) 测试断言改为实际常量 `dpkt.pcap.DLT_RAW`(=12), 维持"保持不变"合同; 或 (b) 明确采用 101 并作为兼容变化在 §2 披露、送第三方确认。

### F2(低至中): 主循环 1s → 100ms 轮询未在 §2 兼容变化中披露

- 当前 `fakenet.py:534` 为 `time.sleep(1)`; 方案 §4.4 改为"最长 100 毫秒"。
- 影响: stop flag 响应延迟从 1s 降至 100ms(正向), 主循环每秒多唤醒约 9 次(可忽略), 但对停表时序、日志排空时机有细微影响。
- 建议: 在 §2 兼容变化清单中披露该轮询周期变化, 并说明 100ms 的选择依据(capture-fatal 响应延迟与 CPU 唤醒的折中)。

### F3(低): `-converted.pcap` 与外部工具 `MalwareWorkHelper.fakenetng_convert()` 的命名兼容声明无法在仓库内核验

- 该工具不在本仓库中; 命名兼容是外部约定。建议在方案中标注"该外部工具由项目方确认其 `-converted.pcap` 命名合同", 避免审核方把无法核验的外部事实当作已证明前提。

### F4(低): 已知 version 截断包双写的下游解析器行为建议列入验收

- 截断"IPv4 包"(如首字节 0x45 但仅数字节)会被双写, Ethernet 版再增 14 字节头。这维持现有 RAW 行为且对称, 但建议在 §7.3/§7.4 的独立解析器比较中确认下游工具(Wireshark 等)对截断包不报错阻断验收, 并把"截断包仍可被独立 reader 读取"列为断言。

### F5(低): 方案未声明代码基线

- 本方案是跨 Windows/Linux 的新抓包能力方案, 但未写明审计/实施基线 commit(与同目录其他方案不同)。建议在头部补基线声明(如 `e0ef8cd`), 使后续"实际结果追加"可追溯。

### F6(低): 性能 harness 建议使用锁文件内 dpkt 版本并在验收记录中登记 venv 实际版本

- 已确认锁文件固定 dpkt==1.9.8; 建议实施阶段把性能测试与验收包的 venv 绑定到同一锁文件, 并把实际 dpkt/平台/卷信息写入方案末尾的实施核实记录(方案已要求记录机器/Python/dpkt/卷类型, 无新异议, 仅确认)。

## 3. Fallback 复核(v1 添加的 fallback 及合理性)

| 方案中的 fallback/确定性选择 | 性质 | 合理性 |
|---|---|---|
| 初始化失败: 只删除本次启动新建的零记录文件(§4.2) | 事务回滚 | 合理; 依据 `created_by_this_start` 逐文件标记, 不按路径/glob 猜测 |
| 平台启动失败: 零记录删空头文件, 有记录保留部分文件并标记失败(§4.2) | 证据保留 | 合理; 部分证据不伪装成成功 |
| 运行时任一 writer 或 close 失败: 受控停止、非零退出、无单 writer 继续(§4.4/§9) | 显式失败处理 | 合理; 与"不提供单文件模式"合同一致 |
| 空包/未知 version: 双边对称拒绝 + 计数 + 限速日志, 不触发 fatal(§3.3/§4.3) | 输入裁决 | 合理; 避免恶意畸形包终止 FakeNet, 且不破坏双文件对应关系 |
| 测试 seam 注入 writer factory(§6.3/§7.1) | 测试机制 | 合理; 只能由测试 launcher 触发, 生产 INI/环境变量/命令行不可激活 |
| 明确禁止: 单 writer 降级、换目录/改文件名、丢包/采样/异步队列、离线转换补齐、Scapy 备用、自动开启 DumpPackets(§9) | 无 fallback | 全部合理 |
| dpkt/Python 缓冲使错误延迟到 close; 不做每包 flush/fsync(§4.6) | 已披露固有边界 | 合理; 验收以停止后独立 EOF 解析为准 |
| 掉电/强杀下无法跨文件原子一致(§8.1) | 已披露不可消除边界 | 合理; 未夸大为已缓解 |

结论: 未发现 v1 添加不合理 fallback, 也未发现漏报的隐式运行时回退。

## 4. 对现有机制的破坏评估

- **正面**: 方案识别并修复了三个现有真实缺陷——(1) legacy Windows 与 Linux 的 `pcap.close()` 失败会跳过网络恢复(当前代码线性执行, 无 finally 保护); (2) Windows `join(5)` 后不检查 `is_alive()` 即关 writer 的潜在竞态; (3) Linux NFQUEUE 线程异常静默终止 + 无界 `join()` + 无 verdict 滞留队列的风险。这些修复方向与失败关闭原则一致。
- **兼容风险集中且已披露**: RAW 全局头 snaplen 1500→262144(已披露); `self.pcap`/`self.pcap_lock` 移除(仓库内调用方已检索, 无隐藏引用); 双文件输出(已披露); 唯一未披露的是 F1(linktype 101/12)与 F2(100ms 轮询)。
- **对已验收网络策略零热路径影响**: allowlist/takeover/reviewed/burp 配置均保持 `DumpPackets: No`, 双写只在 `Yes` 时生效; 性能门禁(2.5×)只约束 benchmark, 不改变裁决。
- 未发现方案未识别且会破坏现有机制的缺陷。

## 6. 审计结论

- **正确性**: 方案对现状的描述与代码事实吻合(含 dpkt 1.9.8 的 snaplen=1500 默认、不截断语义、微秒精度); 三个现有缺陷识别准确; `DumpPackets` 配置分布属实; 锁文件版本与性能基准一致。发现 1 项中等级事实错误(F1: 测试合同 linktype 101 vs dpkt 常量 12), 需在升版时修正。
- **完整性**: F2-F5 为低等级补强; 风险表(§8)覆盖完整, 掉电/强杀/缓冲延迟边界披露准确, 未发现被低估到影响决策的风险。
- **fallback**: 仅含事务回滚、证据保留、输入裁决与测试 seam, 无隐式运行时回退, 全部合理。
- **建议流转**: 吸收 F1-F5 后升版(v1.1 或 v2)送第三方审核; 按方案自身门禁, 审核通过且项目负责人明确批准前不得实施。本审计未执行任何代码、配置、测试或交付包修改, 未在任何主机或 VM 试运行方案。

## 7. 方案维护方复核、不同意见与驳斥（2026-08-05）

### 7.1 复核范围与结果

维护方以基线`e0ef8cd`、本仓库当前源码、内置`wheelhouse/dpkt-1.9.8-py3-none-any.whl`源码和审计引用的仓库外方法为依据逐项复核，没有运行FakeNet-NG、WinDivert或NFQUEUE。F1-F6中可由事实支持的内容已引入原方案v2；以下仅记录不同意的审计表述，不改写第三方原文。

### R1：不同意“当前空包可能进入RAW文件”的事实判断

**驳斥内容：** 审计§1把“未知IP version/空包可能进入RAW文件”合并判为属实，其中“未知version”成立，“空包”不成立。当前正常Windows/Linux数据面无法构造一个携带空raw的`PacketCtx`并进入`handle_pkt()->write_pcap()`。

**驳斥原因：**

1. `fakenet/diverters/fnpacket.py:68-69`在`PacketCtx.__init__`内首先读取`self._raw[0]`；空bytes会在对象构造阶段抛出`IndexError`，早于`handle_pkt()`及其`write_pcap()`调用；
2. Windows policy路径在`windows.py:753-757`又显式检查`if not raw`并直接记录drop后返回；
3. dpkt自身能够写caplen=0记录，只能证明底层writer能力，不能证明当前FakeNet调用链会把空记录送到writer。

原方案继续要求`DualPcapWriter`防御空输入是合理的独立模块合同和测试需要，但不能反推当前生产路径已经会记录空包。

### R2：不同意“DumpPackets: No意味着对已验收网络策略零影响”的绝对表述

**驳斥内容：** 审计§4所说的“零热路径影响”若仅指没有第二次磁盘I/O，可以成立；若理解为对已验收策略运行行为零影响，则不成立。

**驳斥原因：**

1. v2把`fakenet.py`主循环等待从1秒改为最长100毫秒，该循环在`DumpPackets: No`时仍运行；
2. v2要求为`Fakenet/Diverter`增加幂等停止门闩，Ctrl+C、stop flag、启动回滚和日志排空均经过共用停止控制面；
3. 因此关闭PCAP确实避免双writer的包路径I/O，但不能免除共用控制面回归。

原方案v2已把该风险从“低”修正为“低至中”，并新增`DumpPackets: No`下stop flag、Ctrl+C、日志排空和既有策略回归门禁。

### R3：不同意把“NFQUEUE当前包无verdict滞留”表述为已由静态代码证明的现有事实

**驳斥内容：** 当前Python代码足以证明`LinuxDiverterNfqueue._threadproc()`只捕获`socket.timeout`、没有把其他异常状态传给主循环，且`stop()`使用无显式超时的`join()`；但不足以单独证明C扩展回调异常后当前netfilter包必然保持无verdict并滞留。

**驳斥原因：** 当前包在回调异常时的最终verdict、释放时机及`run_socket()`行为还取决于python-netfilterqueue/C扩展和内核队列状态。本次审计明确没有加载NFQUEUE或执行动态验证，因此该结论只能作为高风险假设和验收目标，不能标为已证事实。

原方案v2仍要求capture-fatal时显式drop当前包，并在隔离Linux环境验证不存在无verdict排队包；这属于待验证的实施合同，不是对现状已完成的证明。

### R4：不同意“snaplen=262144必要且正确”这一过度确定的表述

**驳斥内容：** 审计证明了dpkt默认1500与1514字节Ethernet记录可能形成`snaplen < caplen`，因此“必须显式选择足够的snaplen策略”成立；但没有证明262144是唯一必要值，也没有通过下游工具和双平台动态测试证明该具体数值已经正确。

**驳斥原因：** 其他足以覆盖输入上限的数值或RAW/Ethernet分别设置上限在技术上也可能成立，只是会形成不同的兼容合同。v2选择两个文件统一262144，是为了简化合同、避免常规WinDivert/NFQUEUE记录超限且不预分配内存；它仍会改变RAW全局头，必须由第三方和真实解析器确认。

因此应把262144描述为“已披露、待审核和验收的设计选择”，而不是由静态源码已经证明的唯一正确答案。

### 7.2 维护方流转结论

原方案已升为v2。F1的linktype事实修正和F2的共用控制面披露均为实质性变化，不能沿用对v1的审计结论。v2必须重新送第三方审核；审核通过且项目负责人明确批准前严禁实施。
