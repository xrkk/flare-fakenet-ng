## 2. 根因（已核实到源码与实机日志；行号基于 30e1a75，实施时以函数名/代码片段定位为准）

### 2.1 问题 1：进程网络视图（procview.py）
- **解析永不匹配**：`PROCESS_FLOW_RE`（procview.py:18-20）按单级方括头 + 事件名直随其后的合成格式编写。真实日志（GUI 经 `_poll_log`→`_append_log_text`→`feed()` 喂入的是**日志文件**格式，app.py:2517-2528）实为：
  `08/18/26 08:16:10 PM [INFO    ] [          Diverter] pid=2664 thread=WinDivert PROCESS_FLOW disposition=DIVERT_FAKE domain=- dport=5353 dst=224.0.0.251 pid=2240 process=svchost.exe proto=UDP sport=5353 src=192.168.204.166`
  即两级方括头 + `pid=N thread=NAME ` 前缀，正则不命中 → 窗口 0 行数据，过滤自然"无效果"。
- **无居中代码**：`__init__` 仅 `self.window.geometry('980x560')`（procview.py:67）。

### 2.2 问题 6 与问题 4（同根，两级断链）
- **第一级（核心）——接管 sink 流量被原样放行**：`_handle_policy_packet` 在 Divert 分支（windows.py:1356-1361）**之前**存在 `matches_takeover_sink` 分支（windows.py:1304-1318）：dst==`ExternalTakeoverIPv4` 的本机流量得到 `ALLOW_TAKEOVER_SINK` 判定后**不经改写** `_send_packet` 重注入。而 sink 被策略强制为**非本机**地址（egresspolicy.py:521 拒绝本机 sink；实机 `TAKEOVER_ROUTE_OK` 快照为 on-link 子网路由）——**已证实**：包未改写即重注入、且拓扑内没有任何进程监听 sink 地址；**合理推断（预验留证，见 §5.0-2）**：VM 内 192.168.204.1 是 VMware NAT 宿主机地址，重注入包离开 VM 后死于宿主机，客户端表现为"连接失败"。实机旁证（审计 A-04 修正后表述）：v31 phase2 日志中 msedge 对 192.168.204.1:443 的两条流（sport 49853/49854）自 08:16:10 起 SYN 反复重试，`ALLOW_TAKEOVER_SINK` 事件共 12 次，始终无建流成功迹象（无对应的 DIVERT_FAKE/REINJECT/监听器处理事件）——与"重注入包无监听者"的解释一致：客户端在 TCP 层从未收到应答，重试行为本身即旁证（注：`ALLOW_TAKEOVER_SINK` 事件对同一流的每次 SYN 重试都记录，"每流一次"的是 PROCESS_FLOW）。该分支源自旧设计"域名固定解析到指定 IP 并**放行**流量"（commit 44031b5；文档 `PLAN/2026.08.03/2026.08.03-03-…放行流量方案.md`），与现行"后续直连仍入彀（Divert 兜底）"设计（总纲 §12.32 论证）矛盾，取代声明见 §2.6。`ExternalTakeoverProbe*` 为启动器前置探测（egresspolicy.py:166 注释 "launcher-only"，Start-EgressControl.ps1 在 fakenet 启动前完成），不依赖该运行时分支。
- **第二级——策略拓扑无内容监听器**：GUI/验收产出的拓扑只有 ProxyTCP:8080 + ProxyUDP:38926 + relay + DNS×2。ProxyListener 对入流做 `get_top_listener` 逐 provider `taste()` 分发（listeners/ProxyListener.py:185-209），`Listeners:` 清单键在本 fork 仅为文档（gui/schema.py:431 标注"仅文档"），实例从不创建 → HTTP GET 无分发目标，连接被直接关闭。实机证据：a10 日志探针 GET 的 hexdump 之后**无任何 "Likely listener" 分发记录**。上游原版 `fakenet/configs/default.ini:340-357` 有独立 `[HTTPListener80]`(:80)/`[HTTPListener443]`(:443) 段，直接命中，故原版浏览器能拿到自定义回复。
- **问题 4 是两级断链的下游结果**：流量死在第一级或被第二级关闭 → 监听器从未处理 → 无 NBI。实机证据：a10 报告仅 svchost mDNS 8 行（python 探针的 HTTP **请求已到达监听器**——代理 hexdump 在案——但其 NBI 0 行；探针**应答内容**未被 A10 断言，是否收到非空应答属未证实）；phase2 报告仅 DNS/mDNS 记录。会话与 NBI 机制本身健康：`maybe_redir_port`→`addSession`（diverterbase.py:1927）→监听器 `logNbi`→`sessions[orig_sport]`（diverterbase.py:2102）→报告渲染（phase2 报告含 msedge DNS NBI 证明链路通）。
- **勘误（2026-08-21，审计 A-01，取代 v0/v0.1 的"附带发现"）**：v0 曾断言"phase3 报告 `report_20260818_201630.html` 在实机已生成但未被导出"——**不成立**。该文件实际已在导出目录（43,294 字节；v0 制定时被 `ls | head` 十行截断误判漏看）；验收运行的报告直接生成于各阶段日志目录（进程 CWD，`FakeNet-NG startup: log=…\test\gui_vm\Logs\policy-…` 可证）；GUI 手动会话的报告（包根）已由既有 `test/gui_vm/Export-Logs.ps1` 的 `report_*.html` 模式（:23-24）覆盖。两处导出路径均无缺口，原据此外设的 I8 条目已删除（见 I8 占位）。

### 2.3 问题 5：PCAP 单向
WinDivert 过滤器只有 outbound（windows.py:495-496：`'outbound and (ip or ipv6)'` / `'outbound and ip'`）；全部 `_timed_write_pcap` 写入点只见出站包。监听器应答走环回 inbound、真实服务器应答走外部 inbound，均不经过过滤器。设计使然，非回归。

### 2.4 问题 3：Ctrl+C 双重回车（范围拆分说明）

未坐实假说：conhost 输入缓冲残留（Ctrl+C 处理期间击键被缓冲）。宿主为 Git Bash/MinTTY，无法复现 VM 的 conhost 键序。

### I7 PCAP 双向捕获（需求 5，核心）

- **允许修改**：`fakenet/diverters/windows.py`（`__init__` 状态区 :474-490；主句柄打开点 :945 邻近；主句柄关闭点 :1020 邻近；`stopCallback`:2034 邻近——以实际代码结构为准）；新增宿主测试（见 I9.4）。
- **现状**：§2.3。dual pcap 生命周期由 `DumpPackets` 配置与 diverterbase `_close_capture`/`_capture_writers_safe_to_close` 门控管理。
- **目标行为**：
  1. 当 dual pcap 启用时，在主 WinDivert 句柄就绪后打开**只读捕获句柄**：过滤器 `'inbound and (ip or ipv6)'`（策略模式）/`'inbound and ip'`（接管模式），`priority=1`（主句柄默认 0；两过滤器集合不相交，优先级取 1 仅为满足句柄优先级唯一性）。打开失败按捕获失败处理（`_record_capture_failure` + 受控停机），**不降级为单向**。
  2. 独立 daemon 线程循环：`recv` → `self.dual_pcap.write_ip_packet(bytes(wdpkt.raw))` → `self._inbound_capture_handle.send(wdpkt)`（原样回注，永不修改）。`WindowsError` winerror ∈ {4,6,995} 退出循环（句柄关闭中）；`PcapWriteError` 映射为捕获失败并退出循环（复用 write_pcap 的失败语义，diverterbase.py:1378-1383）。
  3. 停机顺序：先关捕获句柄 → join 捕获线程（超时 5s）→ 再走既有主句柄关闭与 `_close_capture`。捕获线程必须纳入既有的"packet thread 全部停止才允许关 writer"机制（`_capture_writers_safe_to_close` 门，diverterbase.py:845-848），否则 stop() 会以 `capture writer left open` 失败——实施时按主接收线程的同一注册方式接入。
- **捕获范围与开销披露（回应自评 F-07）**：`inbound and (ip or ipv6)` 覆盖**整机入站流量**（含与分析无关的系统流量），与既有 outbound 捕获范围对称；pcap 体积预计约翻倍。`DumpPackets` 既有开关仍是总量控制手段（关闭即无任何 pcap）。
- **前置**：无。**依赖/顺序**：独立；P14 验收依赖本条。
- **实施者可裁决**：线程命名、超时值（5s 可微调）、错误日志措辞。
- **回流边界**：VM 实测 WinDivert 拒绝该过滤器/优先级组合（打开失败）→ 停止并回流（H2）；若发现 inbound 环回包在 pydivert 1.4 下不可捕获（P14 失败且日志证明环回 inbound 缺席），停止并回流——不得实施者自行改用其他捕获层。
- **验收**：见 §5.2-P14、§5.1-V6。
